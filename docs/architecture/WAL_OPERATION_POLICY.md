# Android SQLCipher WAL — політика експлуатації

**Узгоджено власником 31.10.2026; PR #29.** Це невелике документальне й діагностичне уточнення наявного Android SQLCipher WAL. Нових фонових служб, довільних таймаутів, лімітів WAL чи змін Windows/iOS тут **немає**.

## 1. Внутрішнє сховище та SAF

Робоча SQLCipher БД `andrey_ceilings_sqldelight_v2.db` та її `-wal` / `-shm` знаходяться в **приватній внутрішній пам'яті застосунку** (`context.getDatabasePath`). Тимчасові SQLCipher-знімки `VACUUM INTO`, перевірка імпорту й staged restore використовують внутрішні робочі файли. Для цього середовища є внутрішній `StorageSpaceGuard` та реальні ізольовані Android `ENOSPC` тести для restore і WAL INSERT.

Переносні `.stpb`, автоматичні копії та PDF експортуються у **вибране користувачем SAF-призначення** (яке може бути внутрішньою спільною папкою, SD-картою або стороннім провайдером). Це **не робоча БД**. Рішення власника: **не додавати до PR #29 окремих стрес-тестів заповнення зовнішніх/хмарних SAF-сховищ**, але **не прибирати обробку помилок запису**. Автоматичне резервування має повідомляти worker про невдачу, прибирати частковий файл, а ручний експорт — показувати невдачу без повідомлення про успіх. Невдалий SAF-експорт не змінює робочу SQLCipher БД.

## 2. Політика checkpoint

- **За замовчуванням залишаємо штатний `wal_autocheckpoint` SQLite/SQLCipher**, як його налаштував поточний WAL-aware open helper. Не призначаємо жорсткі 1000 сторінок навмання: фактичне значення й розмір сторінки читаємо через `PRAGMA`. Параметр є **налаштуванням з'єднання**, його не можна вгадувати з іншої тестової БД.
- **`PASSIVE` тільки за явною дією «Перевірити WAL checkpoint»** у наявній діагностиці. За зайнятих читачів він може залишити кадри неперенесеними; це не привід видаляти файли або блокувати інтерфейс. Тепер показуємо статус останнього ручного запуску **лише в межах цієї UI-сесії**; після її завершення статус не є історичним журналом.
- **`FULL` — лише в контрольованих сценаріях**, де його вже вимагають перевірки/ізольовані процедури. Не запускати `FULL` після кожного заміру/кошторису. Для резервування застосовується консистентний зашифрований `VACUUM INTO`, а не копіювання лише `.db` або вимушений checkpoint для отримання «стабільного файла».
- **Не реалізуємо додаткову фонову службу idle-checkpoint зараз.** Якщо вимірювання згодом виявлять затяжне зростання WAL через довгих читачів, окремо проаналізуємо причину та безпечний idle `PASSIVE`. Не видаляти `-wal`/`-shm` при відкритому драйвері.

## 3. Політика блокувань і надійності

- **`busy_timeout` і `synchronous` залишаємо під контролем SQLCipher / Android open helper**; жодних неперевірених констант у production. Вони відображаються як **поточні прочитані значення**, не як обіцяні рівні продуктивності.
- **Немає blanket-retry для транзакцій створення/перерахунку кошторису.** Після `SQLITE_BUSY` не можна автоматично повторювати операцію з потенційним дублюванням незмінної ревізії. SQLDelight має власну транзакційну перевірку stale source / price state / унікального номера версії, повторна спроба лише як **нова явна дія** з перевіркою.
- Окремі SQLDelight-транзакції на Android можуть починатися як `BEGIN IMMEDIATE` навіть коли тіло лише читає. Їхній `SQLITE_BUSY` проти іншого writer не означає, що звичайний WAL `SELECT` блокує writer: це окремо покривають `SqlCipherSeparateConnectionsTest` та concurrent snapshot tests.
- У разі `SQLITE_FULL`/ENOSPC повідомити про невдалу операцію; **не робити вигляд, що запис збережено**. Реальні ізольовані тести перевіряють rollback, цілісність, відновлення, key, `FULL` checkpoint та cold reopen.

## 4. Діагностика та перевірка зростання WAL

Наявний екран **Налаштування → Діагностика БД → Перевірити БД і кількість записів** тепер додатково **лише читає**:
- `PRAGMA busy_timeout` — мілісекунди; поточний ефективний параметр з'єднання.
- `PRAGMA wal_autocheckpoint` — кількість сторінок; приблизний поріг у байтах рахується як `pages × page_size` лише коли додатній і без арифметичного переповнення.
- `PRAGMA synchronous` — відображає `OFF/NORMAL/FULL/EXTRA` за числовим кодом.
- Фізичні розміри **основного `.db`**, `-wal` та `-shm` у байтах, окремо; актуальні `journal_mode`, `page_size`, `page_count` і `cipher_version`.
- Статус останнього **ручного `PASSIVE`** у межах поточного відкриття екрана.

**Великий WAL сам по собі не є доказом збою:** файл може залишатися фізично виділеним навіть після перенесення кадрів, і розмір фізичного файла не дорівнює кількості неперенесених транзакцій. Не робимо автоматичний `TRUNCATE` тільки за розміром; при стійкому рості вивчити кількість кадрів у результаті checkpoint, довгі читання та реальну нестачу вільного місця.

Новий **`SqlCipherWalOperationalPolicyTest`** на одноразовій ізольованій зашифрованій Android WAL БД:
1. Перевіряє фактичні PRAGMA read-only, не змінюючи `busy_timeout`, `wal_autocheckpoint`, `synchronous`.
2. Створює **160 послідовних транзакцій із вимірюванням реального WAL-файлу** (кожні 40 записів); не припускає абсолютного порога у байтах.
3. Запускає `PASSIVE` після завершення записів; перевіряє завершення, кількість рядків, цілісність, незмінність PRAGMA та доступність даних після **cold reopen**.
4. Записує фактичні параметри й зразки розміру у Android instrumentation log під тегом `SqlCipherWalPolicy`.

До зеленої нової Android CI збірки ці діагностичні зміни **не вважаються прийнятими**. Старі SIGKILL / ENOSPC / backup tests залишаються без змін.

## 5. Що не належить PR #29

Немає окремого керованого користувачем інтерфейсу для зміни WAL-параметрів, сервісу автообслуговування, ручного видалення `-wal`/`-shm`, надмірно частих checkpoint, автоматичних повторів кошторисів, примусового обмеження розміру WAL, підміни збереженої точності вимірів або стрес-тестів стороннього SAF-провайдера. Наступна оптимізація можлива тільки на підставі виміряного регресійного сценарію.
