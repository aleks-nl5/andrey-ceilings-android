# StelaPro — Майстер насамперед: простота UX та порядок розробки

> **Постійний продуктово-процесний контракт, затверджений власником 23.11.2026.**
> Поширюється на всі майбутні та змінювані екрани StelaPro: Android, iOS, Windows, спільний KMP/CMP.
>
> **Головна мета:** майстер має швидко, легко та без зайвих дій виконати роботу безпосередньо на об'єкті.
>
> **Статус:** це затверджені принципи, користувацькі сценарії, правила планування та критерії приймання, **а не доказ, що поточна реалізація вже їм відповідає**. Документ не дозволяє без окремого погодження повний редизайн, зміни БД/прайсу/кошторисів або обхід доменних правил.

## 1. Непорушні UX-принципи

1. **Простий шлях перший.** Базовий замір не має вимагати додаткових елементів, креслярських прив'язок, розміщень, редагування геометрії чи створення кошторису. Розширені можливості з'являються **тільки за потреби**.
2. **Компактність із читабельністю.** Мінімум постійного тексту, зайвих панелей, дубльованих кнопок і переходів. Логічно згруповані, акуратно вирівняні дії; інтуїтивні та єдині для програми іконки. Компактний візуальний розмір **не означає малу touch-target** (орієнтир ≥48 dp / платформні a11y вимоги). Текст і значення не обрізаються.
3. **Стабільний контекст.** Вибір «Початок / Кінець», типу параметра або роботи не переставляє несподівано весь набір кнопок. Однозначно видно, **що саме зараз вибрано та редагується**. Відміна прибирає **всю** відповідну форму/режим; не залишає кнопок без полів.
4. **Натискання має очевидний результат.** Якщо дію неможливо виконати, дати коротку точну причину й спосіб виправлення; не залишати користувача з неактивною дискеткою чи числом, що «не змінилося».
5. **Пояснення за запитом.** Для неочевидного — `?` із коротким контекстним спливаючим поясненням. Для реальних проблем — `!`/warning, підсвічення проблемного поля й конкретна дія виправлення. Без постійних довгих пояснень/футерів. Критичну помилку збереження та ризик втрати даних **не ховати** за іконкою: [контракт довідки](CONTEXT_HELP_AND_FEEDBACK.md).
6. **Небезпечні дії — зліва й червоним.** У діалогах видалення й відхилення незбережених змін руйнівна дія **зліва**, однозначно **червона**, безпечне «Скасувати / Продовжити» **справа**; це постійне правило для нового/оновленого UI.
7. **Безпечне редагування.** Скасування/Back не втрачають незастосовані значення без доречного попередження; видалення/discard позначені як небезпечні дії. Загальний Save — явний та атомарний, із коректними Undo/Redo.
8. **Платформність без компромісів:** спільний CMP UI, світла/темна теми, вузький екран, IME, збільшений шрифт, TalkBack/VoiceOver/клавіатура. Локалізація UI (але не користувацьких назв прайсу). Не міняти точні world-mm, UUID, SQLCipher/CAS, source-of-truth, immutable версії кошторисів/PDF заради зовнішнього вигляду.

**Правило для виправлень:** усунення дефекту не має порушувати вже погоджений UX. Наприклад, обрізання тексту в компактному полі виправляємо коректними *внутрішніми відступами/layout*, а не автоматичним збільшенням погодженої висоти.

## 2. Порядок роботи майстра на об'єкті — пріоритетні сценарії

### A. Мінімальний успішний замір

**Створити замір → увести контур/розміри → вибрати полотно → вибрати основний профіль → Зберегти.**

- Це **повноцінний завершуваний сценарій** без додаткових платних елементів, розміщення, прив'язки до стін чи кошторису.
- Полотно та профіль вибираються з **єдиного прайсу** у чітких, компактних селекторах; активний селектор і зроблений вибір очевидні.
- Тільки реальна невалідність даних/конфлікт запису може блокувати Save; причина й подальша дія зрозумілі.

### B. Додати додатковий елемент без примусової кількості

**«Елементи» → знайти позицію → запропонувати кількість → Додати → Зберегти.**

- Майстру **пропонувати** кількість, але **не блокувати саме додавання роботи** через порожню кількість. Робота залишається в замірі з чесним станом «потрібно вказати кількість», якщо її ще не визначено.
- Поруч — маленька контекстна `?`: **«Без кількості ця позиція не враховується в кошторисі. Її можна вказати пізніше.»**
- Порожня кількість ≠ нуль ≠ одиниця ≠ кількість позначок. Позиція **не має нараховуватися як оплачувана** без коректної заявленої кількості. Кошторис не повинен створювати ілюзії повноти, якщо є невизначені позиції.
- **Додати роботу** і **розмістити її на кресленні** — незалежні наміри. Якщо правила типу/одиниці вимагають визначеної кількості для конкретного *розміщення*, коротко пояснити й запропонувати заповнити її — **не блокувати просте додавання роботи**.
- **Межа реалізації:** сьогодні кількість Unknown доступна лише за певних QuantityMode. Продуктова вимога «додати без примусової кількості» може потребувати окремого явного рішення про доменні правила для інших режимів. Не обходити валідацію й не вигадувати ціну/суми приховано.

### C. Уточнити кількість пізніше

- У списку робіт знайти елемент і швидко змінити **заявлену** кількість; після застосування одразу бачити число в чернетці.
- Заявлена кількість **незалежна** від кількості, довжини та площі розміщень.
- «Довжина/кількість з креслення» — **лише явне перенесення** за підтримуваними правилами, з коротким порівнянням **«Зараз → Буде»** та підтвердженням. Не переписувати ручну кількість мовчки; помилки пояснювати.

### D. Просто розмістити на кресленні пізніше

- Знайти вже додану роботу, обрати зрозумілу дію **«розмістити»**, поставити POINT/LINE/AREA. **Без повторного створення оплачуваної роботи** чи втрати введеної кількості.
- Повторні розміщення і вибір конкретного екземпляра не плутаються з вибором усієї роботи.
- Один тап на об'єкті креслення **вибирає/підсвічує відповідний елемент у списку**, а **не розгортає параметри автоматично**. До точних параметрів — через окрему очевидну дію (або погоджений жест).
- При виборі роботи має бути видно відповідний рядок, за потреби зі scroll-to та коротким підсвічуванням.

### E. Точні параметри та прив'язки — лише за потреби

- Легко відкрити точний редактор POINT/LINE/AREA: відстані до стін, довжина/ширина/діаметр/площа тощо, де це підтримує модель.
- Всі споріднені кнопки — компактно згруповані, по можливості **в один зрозумілий ряд**, з очевидним активним станом. Вибір початку чи кінця лінії не перебудовує непередбачувано картку.
- Чіткі стани: перегляд → вибір → редагування → застосування в чернетці / скасування → загальний Save. Закриття форми не залишає осиротілих кнопок.
- Вершини площинного елемента обробляються без зайвих непрацюючих кнопок; вже погоджені прямі маніпуляції на кресленні не замінювати «декоративними» діями.
- Якщо дія незрозуміла — `?` біля неї, а не довгий пояснювальний блок під карткою.

## 3. Новий обов'язковий процес планування кожного UX-етапу

### Крок 1 — сценарій майстра, **без технічної мови**

Власник описує природно: **«Що роблю → що незручно / чого бракує → що хочу отримати»**. Скриншот із короткою приміткою достатній. Власник **не зобов'язаний** знати Compose/терміни розробників чи придумувати layout-компоненти. Асистент/розробник сам формулює UX-потреби, суперечності, основний сценарій і edge-cases; уточнює лише критично невизначене.

### Крок 2 — цілісний еталон інтерфейсу до коду

Для нової/складної панелі створити і погодити **екран/макет**, а не поодинокі кнопки. Перевірити ширину мобільного телефона, normal/fullscreen, світлу/темну тему, масштаб шрифту, touch targets, focus/IME. Обов'язкові стани: **звичайний / вибраний / редагування / невалідний / заблокований / застосовано / скасування / Save / Back**. Окремо перевірити, що відбувається при повторному тапі й переході на інший елемент.

### Крок 3 — письмовий UX-контракт і критерії приймання

Перед реалізацією зафіксувати в GitHub:
- шлях майстра та **мінімальну** кількість обов'язкових дій;
- розміщення/вирівнювання контролів, ключові іконки та їхні доступні описи, компактність і тексти допомоги;
- **стейт-машину поведінки**: що змінюється після кожного натискання, що залишається на місці, що скидається, що зберігається;
- правила optional/required значень, повідомлень, Undo/Redo, global Save, Back/discard;
- acceptance checklist і достатні UI-регресійні тести, включно з попередніми погодженими рішеннями.

Позначити рішення як **approved / proposed / deferred**, без змішування. Узгоджений макет — **еталон**, а не просто натхнення. **Не починати реалізацію неоднозначного UX до погодження власником.**

### Крок 4 — реалізація **всього сценарію**, не окремих фрагментів

Задача для Codex/розробника є автономною: посилання на еталон, конкретні стани, модельні обмеження, тест-матриця. Реалізувати, наприклад: **вибрати лінію → відкрити параметри → змінити початок/кінець → застосувати → побачити результат → скасувати/зберегти**. Виконати review на узгоджену поведінку, а не тільки compile/API/tests.

### Крок 5 — незалежне рев'ю + physical APK приймання

- Діагностика: logic/domain/undo/save + верстка/padding/text/scroll/selection/disabled states + Android/Windows/iOS релевантні перевірки.
- Перевірити **кожен стан проти еталона**, включно з помилками/виходом; не називати «виправлено» без реального свідчення. Build green ≠ UX accepted.
- Фінальне фізичне APK-приймання робить власник. Він же вирішує Ready/merge; PR залишається Draft до його рішення.

## 4. Керування змінами й уникнення повторних переробок

1. **Затверджений UX не можна змінювати самовільно** через технічну зручність або заради виправлення іншого дефекту. За компромісу — спочатку пояснити обмеження, запропонувати альтернативи й отримати рішення власника.
2. Виправлення оцінювати **на рівні всієї картки й повного користувацького сценарію**, а не лише рядка коду/однієї кнопки. Зберігати попередні погоджені позиції, відступи та послідовність.
3. При новому погодженні **оновити канонічний документ** і додати явне `supersedes` на застаріле правило. Старий discovery залишати для історії, але на початку позначити пріоритет чинного контракту.
4. **Ієрархія вимог:** актуальне явне рішення власника → цей постійний master-first контракт → актуальний stage-specific UX spec → старі discovery/handoff/приклади. Якщо дві актуальні вимоги справді конфліктують, **не вгадувати**: винести на розгляд.
5. Після серії скриншотів зберігати одну контрольну **матрицю відповідності**: «побажання → затверджене рішення → UI-стан → код/тест → APK-результат». Не оголошувати всі зауваження закритими лише на підставі комітів.

## 5. Перший обов'язковий застосунок — P5B #156 / Draft PR #157

Перед Ready переглянути проти цього контракту **разом**: (A) контур + полотно/профіль + Save, (B) додати роботу без кількості, (C) змінити кількість, (D) розмістити раніше додане, (E) компактні властивості/прив'язки POINT/LINE/AREA. Не перевантажувати A функціями B–E. Звірити поточну реалізацію з погодженими скриншотами та новим власницьким APK feedback; за невідповідності зберігати Draft.

**Відомі приклади конфліктів (старі формулювання не актуалізувати бездумно):**
- [P5 UX discovery §6.1](../P5_UX_DISCOVERY.md) та [старий P5B UX §4](../P5B_UX_SPEC.md) описували автоматичне відкриття параметрів після тапу по кресленню. **Пізніше рішення:** один тап виділяє/підсвічує роботу в списку; відкриття параметрів — явна дія.
- [P5B UX §2.1](../P5B_UX_SPEC.md) описував основну текстову кнопку «Розмістити ще» в картці вже наявної роботи. **Пізніше рішення:** компактні іконки **в одному рядку з назвою**, зокрема бінокль «До елементу», окрема іконка розміщення та олівець кількості.
- Початкові розміри/поля в реалізації змінювалися як локальні виправлення, хоча вимога — **компактність без обрізання**. Висоту й внутрішні padding оцінювати разом проти затвердженого макета.

**Це документ вимог і процесу. Він не означає автоматичне схвалення фактичного стану P5B чи завершення перевірок.**
