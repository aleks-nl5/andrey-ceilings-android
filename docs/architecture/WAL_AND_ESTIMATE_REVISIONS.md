## One polygon calculator and schema-driven entry (30 Oct 2026)

New common KMP `CeilingPolygonCalculator` models a simple straight-edged room as an ordered list of integer-millimetre `CeilingPointMm`. It calculates area by the shoelace algorithm and perimeter from all edges (last-to-first included), with exact-integer intersection checks, bounds, precision, duplicate-vertex and self-overlap rejection. This supports concave polygons and either orientation but not holes or curves. `CeilingShapeTemplates` supplies the shape name, ordered measurement keys, visible field labels, and a builder from measurements to vertices. Android CalculatorScreen now generates its fields/dropdown from the registry and calls a single `VerifiedCeilingGeometry.capturedTemplate` entry point; rectangle and right-angle L use identical polygon math for new calculator previews. Additional straight-edge templates will not need a new UI layout or area/perimeter formula.

**Immutable history boundary:** existing schema-v1 frozen rectangle/L source inputs, KMP replay and PDFs remain intact and are never reinterpreted as new vertices. The source of truth remains the frozen immutable revision; do not infer unavailable geometry. The generic schema-v2 `vertices` + `measurementsMm` immutable snapshot, Android reader, version-specific PDF and generic repricing path have now been implemented and tested. The free-vertex editor UI remains future work; do not claim it is released. Curved shapes will need separately versioned segment primitives, not a fictitious polygon approximation.

## First-save Android L-shaped geometry and version-safe PDF (30 Oct 2026)

Android's calculator now offers rectangle and L-shaped rooms through one parameter-driven KMP template registry. For L shapes, the user supplies four dimensions A–D and the template derives E = A − C and F = B − D from right angles; the resulting frozen estimate still contains all six canonical sides. `VerifiedCeilingGeometry.capturedLShaped` performs finite-positive, selected-precision, orthogonal closure and non-fallback-area validation in pure common KMP before pricing. At first INSERT, Android supplies this exact typed geometry to the SQLDelight adapter, which rechecks precision and computed area/perimeter and freezes all six sides, shape and `geometrySchemaVersion` in the immutable v1 input. The compatibility estimate row's length/width are **only the outer bounding dimensions**, never the complete historical geometry.

On reading an L-shaped estimate from SQLDelight, the Android adapter retrieves its original immutable input and validates its six sides, including for duplication, so creating a copy cannot turn L geometry into a rectangle. Historical PDF reconstruction reads the selected immutable revision and renders its six sides, not the bounding rectangle. Direct export of v1 also resolves the immutable SQLDelight snapshot (never mutable UI state). Shared KMP tests cover captured/frozen geometry; encrypted Android WAL tests cover creation, reload/copy, v1/v2 revision and PDF for both versions. No production data migrations are needed merely for the disposable current test DB.

## Extensible frozen geometry foundation (30 Oct 2026)

The immutable `sourceMeasurementJson` now carries an explicit `shape` and `geometrySchemaVersion=1` for newly created rectangular estimates. The cross-platform `FrozenGeometrySnapshotSchema` lists exact required shape-specific input keys; its Android SQLDelight reader rejects unknown versions, shapes, missing sides, and unexpected data. Existing older test snapshots can be read without rewriting them. Shape-specific numeric validation is still performed by KMP, independently from the schema/key check. Every revision retains its original inputs, historical amounts, and document identity.

Only rectangle and six-side orthogonal L-shape have supported immutable replay contracts today. Future T/U/trapezoids/polygons/arcs must introduce complete typed inputs (including required vertices/diagonals/curve definitions), verified calculations, and cross-platform tests. Do not invent geometry from area/perimeter; do not reinterpret historical v1/v2/v3 when adding a shape. Android L input UI + full first-save source remain a separate implementation gate.

## Why one PR?

Both operations must preserve a consistent, immutable commercial history while the encrypted database is active. The shared storage tests and backup/restore acceptance gate should cover v1, v2, v3 together, including WAL, rather than allowing an untested combination to reach `main`.

This does **not** mean enabling WAL before ensuring a consistent encrypted snapshot. Implementation should be split into independently testable commits inside this branch.

## Ground truth

- Android SQLDelight / SQLCipher currently reports `journal_mode=delete` on the user's device.
- `estimate_series`, `estimate_revisions`, `estimate_revision_lines`, transactional v1 and `appendRevision()` already exist from PR #27.
- PR #28 displays only human-readable estimate numbers; full document and series UUIDs stay private.
- Existing portable backup uses `wal_checkpoint(FULL)` followed by direct file copy. **This is not a safe WAL snapshot under concurrent writers**.
- Existing restore writes the live DB file, and currently deletes WAL/SHM files around the replacement (including after reopening). This must be redesigned before WAL rollout.
