## Залишки першого CMP зрізу та перехід до наступних PR (31.10.2026)

Перший CMP прайс #36 закрито після підтвердження Android UX/CRUD і Windows/iOS CI, **не після повної продуктово-функціональної рівності трьох платформ**. Фінальний вигляд редактора: категорія (60%) / оригінальний селектор одиниці (40%) в одному рядку; інформація про незмінність історичних кошторисів (65%) / ціна продажу (35%) в наступному; швидке редагування — окремо. Android сторінка має 16dp зовнішнього горизонтального відступу, як налаштування.

- [#42](https://github.com/aleks-nl5/andrey-ceilings-android/issues/42): Windows GUI smoke/installer/vault/Inter; runnable iOS host/Keychain/Inter/UI smoke/PDF/backup.
- [#45](https://github.com/aleks-nl5/andrey-ceilings-android/issues/45): опціональний shared typed UI-state/intent/presenter після стабілізації, не відкладений функціональний CRUD.
- [#44](https://github.com/aleks-nl5/andrey-ceilings-android/issues/44): реальний зв'язок із цінами нових кошторисів, frozen snapshots; [#37](https://github.com/aleks-nl5/andrey-ceilings-android/issues/37): необов'язкові фінансові компоненти. Також #38–#41 — окремі майбутні функції.

## 1. Мета і продуктове рішення
Перенести реальний прайс із Android `app/.../PriceListScreen.kt` у спільний Compose Multiplatform UI (`:shared`), не переписуючи чинний спільний KMP `PriceRepository`, SQLDelight чи розрахункове ядро. UI має бути **один**, із адаптивним компонуванням для Android/iOS touch та Windows keyboard/mouse. Реальний Android — збережений візуальний та поведінковий еталон.

**Цільова майбутня модель — розширений прайс, але обов'язкова лише ОДНА ціна: ціна продажу.** Вона йде в нові кошториси. Закупівельна ціна, монтаж, додаткові витрати, націнка — за бажанням користувача. Розрахункові собівартість, маржа й прибуток показувати лише за достатніх даних; порожнє значення не є нулем. **У першому CMP PR не змінюємо чинне поле `price` та фінансову модель** — зберігаємо сумісність і виносимо нові поля в issue #37.

## 2. Фактичний стан після merge PR #29
- Android: `PriceListScreen` читає `PriceItemEntity` через платформний DAO-адаптер, відображає групи категорій та вміє створити/редагувати/soft-delete; без пошуку та швидкого редактора ціни. Під час створення вводяться title, category, unit, price.
- `:shared`: `PriceRepository`, SQLDelight `price_items` із `id`, `code`, `title`, `category`, `unit`, `price`, `updatedAt`, `uuid`, `deletedAt`; UNIQUE(`category, code`) для активних; `observeAll` Flow, `upsertReturningId`, soft-delete.
- Примерний демо-прайс: 22 позиції у групах «Полотна», «Профілі», «Роботи», «Освітлення», «Додаткові роботи»; демонстраційна ціна не є рекомендацією ринку.
- Windows `:desktopApp` наразі показує `SharedFoundationStatus`, не реальний прайс. iOS: компілюваний KMP framework і тести, але не готовий runnable host. Не заявляти product parity там, де його ще немає.
- Ревізії кошторисів #29 незмінні: зміна/видалення прайсу **не змінює** історичні PDF і ціни. При ручному перерахунку зберігати існуючі захисти UUID/stable code/unit/token/transaction.

## 3. Цільовий UX спільного екрана
### 3.1 Перелік та навігація
- Заголовок «Прайс-лист», основна кнопка «Додати», зрозумілий статус БД без фальшивого нескінченного завантаження.
- Швидкий пошук по назві й службовому коду (без показу громіздкого UUID); по можливості регістронезалежний; локальне фільтрування спостережуваного каталогу без додаткових звернень до БД на кожен символ.
- Категорії/чипи: Усі, наявні (Полотна, Профілі, Освітлення, Роботи, Додаткові роботи) + користувацькі; вибір категорії зберігає пошук. Категорії формуються з фактичних даних, без hardcoded набору як єдиного джерела правди.
- Кожна позиція: повна читабельна назва, продажна ціна з валютним форматуванням, одиниця, за потреби категорія, можливість відкрити редактор. Не показувати всі фінансові поля на картці.
- Empty, filtered-empty, loading, DB-unavailable, failed write й success — різні стани. Явна діагностика без витоку шляхів/SQL/персональних даних.
- Не робити окремого навмисно повільного запиту для кожного рядка; `LazyColumn`/desktop lazy list, стабільні keys UUID, пам'ятати позицію скролу/пошук при поверненні.

### 3.2 Редагування
- **Натискання на назву/рядок** → повний редактор: назва, категорія, одиниця вимірювання, **обов'язкова ціна продажу**. Службовий код/UUID не редагувати у звичайному UI.
- **Натискання на ціну** → компактний швидкий редактор тільки ціни із `Зберегти`/`Скасувати`; не зберігати кожен натиск клавіші; перед записом нормалізувати десяткову кому/крапку і перевіряти валідність/невід'ємність/скінченність.
- Створення позиції: зрозумілі поля й помилки, обирати наявну категорію або вписати нову назву; зберігати правильний стабільний унікальний код без timestamp-колізій і без перевизначення UUID чужого рядка. Остаточна стратегія генерації коду — окремо затвердити на рівні KMP.
- Під час зміни `unit` або `code` не підміняти історію/семантику; зміна одиниці у повному редакторі потребує явного попередження/валідації з урахуванням реального повторного перерахунку. Без неявного перетворення `м²` ↔ `шт.`.
- Видалити = soft-delete `deletedAt`, лише після підтвердження; не переносити в новий каталог інші/помилкові ціни і не підставляти нулі. Помилка транзакції повинна бути видимою.
- При виході з незбереженими змінами — свідоме підтвердження відмови; повторне натискання `Зберегти` не повинно створити дві позиції.
- Актуальний `Flow` із SQLDelight оновлює UI після CRUD; зберегти реактивність й відсутність блокувань UI thread.

### 3.3 Адаптивність
- Android/iOS: одна колонка, зручні touch targets, короткі ряди/картки, нижня шторка або екран редактора залежно від розміру/клавіатури; системні inset/edge-to-edge і чинна навігація.
- Windows: табличний список із колонками назва / одиниця / ціна, категорії збоку за достатньої ширини, редактор у правій панелі/діалозі; wheel, pointer hover/focus, Tab/Enter/Escape. Не розтягувати картки з Android на 1400px.
- Один `PriceListState` і одна семантика подій `PriceListIntent`; змінюється layout, а не бізнес-правила/збереження.
- Спільна тема: наявні світла/темна/системна, графіт/бірюза, Inter, Material 3, розміри, поля, календар/навігація де релевантно. Android rendering — еталон, не створювати в PR масштабний редизайн.

## 4. KMP/CMP структура
Запропоновані компоненти (назви умовні, можна адаптувати до структури коду):
- `PriceListScreen` (`commonMain`) — чистий Compose UI, без Android imports, незалежний від SQLCipher/файлових API.
- `PriceListState/PriceEditorState/PriceListIntent` — спільні моделі з UI validation, search/filter/sort, explicit save/cancel; розділити непідтверджену чернетку й persisted entity.
- `PriceListPresenter` або store/view-model — спостерігає `PriceRepository.observeAll`, викликає KMP use-cases для CRUD; усі DB операції поза UI thread. Обробити конкурентні редагування, safe lifecycle й cancellation.
- `PriceRepository` із чинної SQLDelight є source of truth; не дублювати `PriceItemDao` як другу бізнес-логіку. Android driver/SQLCipher WAL лишається в app platform host, desktop driver/key storage — платформні.
- Сталі UUID/code і soft-delete, актуальні timestamps. Для перепрайсування старих кошторисів — лише наявні явні preview/revision механізми.
- Platform adapters лише для OS доступу/теми/зашифрованої БД, не для business validation. Не використовувати iOS mock CRUD як proof.

## 6. Розширена фінансова модель (прийнятий контракт для майбутнього #37)
| Поле | Обов'язковість | Пояснення |
| --- | --- | --- |
| `salePrice` / ціна продажу | **Так** | Єдина необхідна ціна, в одиницях позиції; йде в нові кошториси |
| `purchaseCost` / закупівля | Ні | Немає введення → unknown, **не нуль** |
| `installationCost` / монтаж | Ні | Не дублювати монтаж із окремих робіт у кошторисі |
| `otherDirectCost` / додаткові витрати | Ні | Не потрібно для створення позиції |
| Націнка (сума / відсоток) | Ні | Може пропонувати продажну ціну, але не змінює її мовчки |
| Собівартість, прибуток, маржа | Похідні | Лише за достатньої кількості відомих даних, інакше «недостатньо даних» |

Приклад: позиція «ПВХ полотно матове» з `salePrice = 290 ₴/м²`, а решта полів порожні, **є повністю валідною**; без закупівельних даних не можна показувати вигаданий прибуток. Якщо всі складові витрат свідомо задані нулями, допустима нульова собівартість — на відміну від `null`.

**Рішення щодо способу розрахунку націнки, округлення, відображення внутрішньої маржі, формату збереження й відмінності товарів/послуг прийматимемо в issue #37 до написання нового фінансового коду.** Зараз не нав'язувати користувачу непотрібні поля та не друкувати внутрішню собівартість у клієнтських PDF.
