# Багатомовність StelaPro — постійний архітектурний контракт

> **Рішення власника: 22.11.2026. Статус: вимогу зафіксовано; реалізацію ще НЕ виконано.**
> Це наскрізна вимога для Android, iOS і Windows із KMP + Compose Multiplatform (CMP).
> Документ не дозволяє самостійно змінювати функціональність, БД чи поточні P5 PR без окремого погодженого завдання.
> Спільні правила також наведено в [AGENTS.md](../../AGENTS.md), послідовність робіт — у [roadmap](../PROJECT_ROADMAP.md).

## Мета та принципи

- **Українська — базова (source/fallback) мова продукту**, але мова інтерфейсу не має бути зашита в код, доменні моделі або базу як єдиний можливий варіант.
- Архітектура підтримує довільну кількість локалей без окремої реалізації кожного екрана для Android, iOS і Windows. Конкретні наступні мови й графік їх появи погоджує власник.
- Для нових користувацьких текстів — **ресурсна локалізація** (ціль: Compose Multiplatform Resources у `:shared/commonMain`, з тонкими платформними адаптерами там, де це необхідно). Імена ключів стабільні; переклади не визначають ідентичність або бізнес-поведінку.
- Не додавати нових текстових UI-літералів у `Text(...)`, діалогах, повідомленнях, accessibility labels, системних сповіщеннях і PDF-генераторах. Винятки: справжні користувацькі дані, технічні коди/протоколи, тести, логи та свідомо нелокалізовані назви. Поки спільний ресурсний механізм не заведено, новий UI-текст слід ізолювати, а не розмножувати жорсткі рядки.
- Мова застосунку — окреме налаштування: `Системна` (системна локаль за наявності перекладу) і явний вибір підтримуваної мови; за відсутності перекладу — прогнозований fallback українською. Вибір зберігається та діє в межах платформи; live-перемикання, перезапуск/відновлення й синхронізація UI-state потребують окремих тестів.
- **Мова інтерфейсу, мова документа, валюта та регіональні формати — різні поняття.** Дата, час, число, валюта, одиниці та правила множини мають визначатися явно, без підміни грошової або вимірювальної точності.
- Не впроваджувати машинний переклад, зміну користувацьких назв, міграції збережених рядків або автоматичну конвертацію валют як побічний ефект локалізації.

## Підтверджений стан коду (вибірковий аудит main, 22.11.2026)

Це **не** повний інвентар усіх ресурсів та рядків.

| Шар | Приклад поточного зв'язування з українською | Заплановане відокремлення |
| --- | --- | --- |
| CMP екрани й навігація | `ObjectsClientsScreen.kt`, `MeasurementCreateScreen.kt`, `AppNavigationState.kt`: видимі українські літерали | Спільні ключі ресурсів, параметризовані рядки, plural forms |
| Android host/налаштування | `SettingsScreen.kt`: «Мова / Українська / UA» як статичний рядок; тексти повідомлень і помилок | Спільний стан мови, platform-specific інтерфейси без дублювання перекладів |
| Доменні статуси | `ProjectStatuses.kt`: технічний `wireId` + український `label` | Стабільний статус/ID у моделі; окреме локалізоване presentation label |
| Дати й числа | `DashboardDateTime.kt`: українські місяці; `MeasurementFormatting.kt`: зафіксована десяткова кома | Локалезалежне відображення, окремо точний ввід/математика/storage |
| Прайс | `StarterPriceCatalog.kt`: початкові назви груп і позицій українською, але вони стають редагованими даними БД | Перекладати **лише елементи інтерфейсу прайсу** (кнопки, поля, повідомлення). Назви груп і позицій, включно з початковими, залишати точно як записано |
| Документи | `EstimateDocumentPages.kt`: «Кошторис робіт», «Ціна, грн» тощо | Локалізовані шаблони документа без зміни фінансових frozen даних |

Відсутність інфраструктури перекладів для більшості поточних CMP екранів не означає, що слід одномоментно змінити всі екрани або перекладати записи БД.

## Захист моделі даних, прайсу і документів

1. **Технічні ідентифікатори незмінні**: `wireId`, коди позицій, ID категорій/ролей, статуси, структури серіалізації, SQLDelight та SQLCipher не залежать від локалі. Локалізований підпис не має ставати ключем для пошуку, рівності або правил розрахунку.
2. **Прайс — індивідуальні дані користувача, не об’єкт локалізації.** Назви **всіх позицій** (також початкових/seed) та редагованих груп зберігаються й показуються **дослівно, мовою та формулюванням користувача**, незалежно від мови застосунку чи PDF. Не створювати автоматичні переклади, альтернативні локалізовані назви, авто-перейменування, переведення seed-рядків за локаллю або пересівання каталогу. Змінювати назви може лише користувач явною дією в редакторі. Локалізуються лише власне UI написи прайсу — «Додати», «Назва», «Ціна», помилки та підказки, а не його вміст.
3. **Frozen кошториси й PDF**: незмінні v1/v2/v3, точні cents, назви позицій, кількості, одиниці, версії, статуси/selected pointers та незмінний provenance не переписуються. Локалізація оформлення під час перегляду/експорту може перекладати заголовки/системні підписи, **але назви позицій із прайсу у рядках кошторису залишаються дослівними** навіть якщо мова документа інша. Не змінювати збережені поля або історичні фінансові значення. Мову нового PDF і політику перевидання старого документа погодити окремо.
4. **Валюта та числа**: не вважати, що переклад автоматично змінює UAH на іншу валюту; не змінювати pricing, rounding, precision, `DecimalInputField`, введення `.5` або парсинг persisted numeric data побічно. Окремо розрізняти presentation formatting, ввід і wire/storage формат.
5. **Резервні копії, імпорт та синхронізація**: локаль не повинна змінювати семантику збережених ID, snapshot proofs, restore або майбутніх wire payloads. Ніяких схемних міграцій лише заради UI-перекладу без окремого обґрунтування.

## Послідовність робіт (окремі погоджені задачі/PR)

- **L0 — інвентаризація.** Перевірити `:shared`, `:app`, `:desktopApp`, iOS host, повідомлення в domain, PDF, seed data, accessibility, notification/error texts; відмітити, що є UI, а що storage/code/user data. Зробити вимірюваний baseline.
- **L1 — фундамент.** Додати Compose Multiplatform Resources/адаптери, українські ресурси та fallback; типізовані або стабільні ключі й параметризовані тексти; модель налаштування мови (system/explicit), persistence і спосіб оновлення Compose UI на платформах. Не маскувати відсутні переклади.
- **L2 — поступова міграція інтерфейсу.** Спочатку спільні навігація/тема/налаштування, далі екрани, статуси, повідомлення, дати/числа й accessibility. Робити разом з регресійними тестами, не змінюючи UX без причини.
- **L3 — інтерфейс прайсу і документи.** Локалізувати лише кнопки, заголовки полів, підказки й помилки редактора прайсу, **ніколи назви позицій та груп**. У preview/PDF перекладати лише системні заголовки/підписи, показувати назви рядків точно як у збереженому кошторисі; визначити окреме налаштування мови документа без змін frozen фінансів.
- **L4 — друга локаль + перевірка.** Після вибору мови власником довести фактичну роботу двох локалей на Android/Windows/iOS, включно з вузькими екранами, довгими рядками, множиною, доступністю, форматом дат/чисел, зміною мови без втрати стану. Додавання нової мови далі — ресурсна задача, не нова реалізація UI.

L0/L1 бажано виконати невдовзі, щоб кожен наступний CMP-екран не збільшував борг. L2/L3 допускають інкрементальну міграцію; не блокувати поточні P5 задачі до окремого рішення власника.

## Автоматичні перевірки / Definition of Done

- На першому етапі впровадити **baseline-aware** lint/static checks для нових hardcoded user-facing literals; існуючі випадки інвентаризувати, а не ламати збірку тисячами історичних false positives. Уточнити whitelist для логів, технічних кодів, даних та тестових fixture.
- Перевіряти відсутні ключі/аргументи форматування, plural forms, fallback українською, зміну мови/перезапуск, довгі тексти/переноси й accessibility.
- Golden/регресійні тести мають доводити, що зміна мови **не змінює** DB даних, **назв позицій і груп прайсу (включно з seed), їхніх цін, назв рядків у PDF**, numeric math, frozen vN, PDF financial totals, SQLCipher backup/restore.
- Перед merge — відповідні shared/JVM/Android/Windows/iOS тести на фінальному SHA, незалежний review, owner APK acceptance за чинним процесом. Не вимикати перевірки, щоб «пройшло».
- У кожному UI PR окремо вказувати: **нові написи локалізовані чи тимчасово ізольовані**, які існуючі залишилися технічним боргом і чи зачеплено PDF/data/formatting.

**У цьому документаційному PR немає реалізації, реальних перекладів, нової локалі, CI gate або зміни БД.** Всі технічні вибори підлягають перевірці на фактичних версіях CMP/KMP під час L1.
