# Етап 2 — контроль Go/KMP та єдині правила розрахунків

**Стан на 29.10.2026.** Робоча гілка: `feature/kmp-calculation-parity`, PR #23 (Draft). Android **поки використовує Go/AAR**, KMP є незалежним еталоном для порівняння. Не видаляти Go та не об'єднувати PR без перевірок.

## Рішення власника: точність вимірювань

- Одне глобальне налаштування із збереженням між запусками: **10 см, 1 см, 5 мм, 1 мм**. Тип: `MeasurementPrecision` у `:shared/commonMain`; Android зберігає `enum.name` в preferences.
- Вибраний крок застосовується **до розмірів приміщення**, **периметра**, **площі** (крок²), **довжин додаткових робіт**, **довжин складних конструкцій**, **збережених нових замірів** і кількостей лінійних позицій кошторису. Кількості предметів у штуках не трактуються як метри.
- `Go` та `KMP` отримують ту саму точність; для Go вона передається в `geometry.precisionStepMeters` і `cost` використовує її після побудови геометрії. Відсутній крок у тестових API лишає початкову поведінку для контрольних parity fixtures; UI завжди задає крок.
- **Округлення грошей — незалежне правило**, наразі до цілої гривні із `half-away-from-zero`. Ніколи не округлювати гроші до 5 мм. Налаштування грошової точності за потреби оформити окремо.
- У новому `detailsJson` записується `measurementPrecisionMeters`; екран кошторисів та PDF беруть точність збереженого кошторису, а не поточні налаштування. Нові заміри зберігають готові округлені результати (окреме поле точності в таблиці замірів поки не додано).
- Консистентність Go/KMP і реальних екранів/друку треба підтвердити фінальним CI та smoke-тестом.

## Рішення власника: незалежні від назви технічні коди

- Для додаткових робіт встановлено єдині коди, що використовуються як ключі *нових* `detailsJson` і прайсу: `light.line`, `light.spot`, `light.chandelier`, `work.shadow_profile`, `work.floating_ceiling`, `work.pipe_pass`, `work.curtain_niche`, `work.extra_corner`, `work.hard_wall`.
- `GX53` більше немає в нових назвах та кодах: **`light.spot` / «Точковий світильник»**.
- У Go API поля кількості іменуються `lightLineMeters`, `spotCount`, у Kotlin також; в базі кошторису зберігаються **канонічні коди**, а не людські назви полів.
- `EstimateLineItem.code` зберігає ідентичність позиції для збережених рядків та PDF; підпис `title` — лише відображення.
- Матеріали/профілі в Android runtime та в БД зберігаються через їхні стабільні машинні ідентифікатори; відображувані українські назви не передаються як параметри розрахунку.
- **Міграції або сумісності зі старими тестовими кошторисами немає за явним рішенням власника.** Нові JSON-контракти є одним джерелом правди, без старих alias.
