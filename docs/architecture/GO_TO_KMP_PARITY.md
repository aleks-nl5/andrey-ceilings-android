# Етап 2 — Go/AAR → Kotlin Multiplatform: контроль відповідності

**Початок:** 2026-10-29, після злиття PR #22. **Гілка:** `feature/kmp-calculation-parity`. Цей документ описує перший безпечний зріз етапу 2, а не готовий production-cutover.

## Вихідний стан

- Android продовжує використовувати `Mobileapi.calculateJSON()` / Go/AAR для **всіх** фактичних розрахунків. `CeilingCalculator` лише формує JSON, підставляє прайс і читає результат.
- `KmpCeilingCalculator` у `:shared/commonMain` відтворює чисті формули `go-core/core/calculator.go`. Ні Android UI, ні PDF/збереження поки не переведені на KMP-двигун.
- Розрахунки KMP розраховані на скінченні (`finite`) величини, як у поточному адаптері Android; окремо треба визначити контракт для NaN/Infinity та невалідних даних, перш ніж викликати KMP із UI.
- Сховища SQLDelight/SQLCipher, резервні копії, ключі й тема лишаються без змін.

## Крок 2.1 — референсні значення Go і незалежне ядро KMP

- [x] Зберегти поточні Go-функції й Android runtime без змін.
- [x] Додати окрему KMP-реалізацію геометрії, вартості, опцій та матеріалів/профілів.
- [x] Створити однакові golden vectors у `go-core/core/parity_vectors_test.go` та `shared/src/commonTest/.../KmpCeilingCalculatorParityTest.kt`.
- [x] Відтворити Go `math.Round` (half-away-from-zero), а не Kotlin `round` (ties-to-even).
- [ ] Отримати зелені Go, Android, JVM/Windows та iOS Simulator CI на **останньому коміті** гілки.
- [ ] Розширити тести на історичні реальні кошториси, довільні прайс-позиції, порожні/некоректні значення, межі й різні порядки округлення. Не позначати 100% parity до цих перевірок.

## Крок 2.2 — узгоджені підсумки кошторисів

**Відомий ризик:** Go використовує ключі `lightLinesMeters` і `spotsGX53Count`, тоді як побудова рядків збереженого кошторису в `EstimateLineItems` читає `lightLineMeters` та `spotsCount`. Потрібно перевірити фактичний формат `detailsJson` у UI перед виправленням і додати end-to-end регресійний тест: **калькулятор → збережений кошторис → рядки → PDF**. Не маскувати розбіжності рядком «Коригування округлення».

- [ ] Перевірити назви ключів у збереженні, копіюванні й PDF.
- [ ] Усунути різницю додаткових робіт та захистити тестами обидва формати (якщо старий був збережений).
- [ ] Розвести розраховані, збережені й виведені величини так, щоб зміна прайсу не переписувала історичні суми.

## Крок 2.3 — інтеграція з Android без регресії

- [ ] Порівнювати Go й KMP на ідентичному запиті, включно зі значеннями поточного прайсу, на різних екранах.
- [ ] Перемкнути один ізольований сценарій після parity; не викидати Go/AAR до повного приймання.
- [ ] Перевірити фізичний Android: розрахунки, додаткові роботи, збереження, перезапуск, PDF та резервування.
- [ ] Зелений CI Android / Windows JVM / iOS Simulator після фінального перемикання.

## Далі

Після підтвердження нового ядра починати **етап 3** — перенесення робочого UI у Compose Multiplatform, починаючи з прайс-листа. Розвиток Windows/iOS host і майбутня мережева синхронізація лишаються окремими PR.
