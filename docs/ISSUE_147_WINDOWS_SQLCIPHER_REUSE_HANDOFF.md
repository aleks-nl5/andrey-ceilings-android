## Why this issue exists: measured facts, not a speed guess

Owner-merged [PR #135](https://github.com/aleks-nl5/andrey-ceilings-android/pull/135) measured real encrypted Windows SQLCipher JDBC on [FULL run 44953631075](https://github.com/aleks-nl5/andrey-ceilings-android/actions/runs/44953631075), commit `3b20ed0`, artifact `windows-sqlcipher-jdbc-profile` ID 14729282221. `SqlCipherWindowsConnectionProfileTest`: eight independent physical opens; DriverManager median **0.3 ms**, first `SELECT count(*) FROM sqlite_master` median **241.9 ms** (1943 ms total); eight SQLDelight reads outside transaction median **241.0 ms** each, while eight identical reads inside one pinned SQLDelight transaction each took **< 0.1 ms**. Do NOT interpret the pinned read-only benchmark as including the transaction's begin/commit/physical-open cost. Attribution to a specific native KDF phase remains unproven.

Same SHA: 500 JUnit cases / zero failures, Windows Gradle FULL **1h23m14s**. The `PriceCatalogWindowsCipherTest` worst methods were ~672 s and ~554 s; `MixedDetailsSceneTest.allMixedOrdersUseProductionDetailsAndOneSaveOrExplicitDiscard` ~818 s. These are measured hotspots; benchmark exact impact rather than asserting the entire duration is connection overhead. Never substitute cached Gradle results for test execution.

## Confirmed production entrypoints and constraints

- `shared/src/jvmMain/kotlin/com/andreyceilings/shared/db/SqlCipherWindowsDriverFactory.kt` defines `ConfiguredSqlCipherJdbcDriver : JdbcDriver`. Outside a transaction it obtains a new configured physical `Connection` per SQL statement and closes it; inside a transaction SQLDelight pins one connection. `executeQuery` has an essential `WITH ... RETURNING` compatibility adapter. `execute` specially consumes `PRAGMA user_version = N` on the transaction connection. Do NOT break either behavior, and keep all existing tests.
- `shared/src/jvmTest/kotlin/com/andreyceilings/shared/db/SqlCipherWindowsConnectionProfileTest.kt` contains the currently successful diagnostic test; extend it with actual logical/physical counts and end-to-end timings WITHOUT writing secrets, SQL, file paths, database contents, or user input.
- `shared/src/jvmTest/kotlin/com/andreyceilings/shared/db/SqlCipherWindowsDriverTest.kt` and `SqlCipherWindowsReturningTest.kt` verify wrong-key, real encryption, foreign keys, DML RETURNING and transaction semantics; `PriceCatalogWindowsCipherTest.kt` verifies migrations, concurrent writes and reopen. Desktop `MixedDetailsSceneTest.kt` uses the encrypted driver when running on Windows.
- `desktopApp/src/main/kotlin/com/andreyceilings/desktop/DesktopPriceDatabase.kt` explicitly drains relevant in-flight measurement writes/reads before driver close. Coordinate the new driver's own closing lifecycle with this flow, including close/read/write races.
- SQLDelight pinned dependency `2.4.1`, SQLCipher JDBC core/runtime `0.2.13`. Inspect the exact upstream `JdbcDriver` implementation and actual native JDBC facade, not an assumed later version. Check SQLDelight's connectionAndClose(), ThreadLocal transaction manager, nested transaction handling, begin/commit/rollback calls and `closeConnection` call sites. Check the actual coroutine dispatcher/hopping semantics in this app. Do not assume a single JDBC Connection may be used concurrently from multiple threads, or that `limitedParallelism(1)` guarantees OS-thread affinity.
- Windows file and native locks, WAL, encrypted `VACUUM INTO` backups, restore/reopen, migration `PRAGMA user_version`, optimistic CAS, immutable financial revisions, and key ownership are non-negotiable invariants. No shared SQLite cache mode, plaintext fallback, KDF reduction, native global singleton, schema/data migration or Android/iOS behavior changes.

## Mandatory implementation sequence

1. **Source audit and competing designs before changing behavior.** Study the pinned SQLDelight and JDBC native sources, all desktop callers and asynchronous work, existing test suites. Compare (A) small bounded exclusively leased physical connection pool, (B) serialized session/dedicated-thread execution, and (C) per-thread cache. Explicitly document correctness and lifecycle tradeoffs; reject unbounded per-thread retention and unsafe across-thread reuse. Pool size is a measured design decision, not a magic number. If core native implementation does not support safe re-leasing, stop with research and propose a smaller follow-up. Do not switch transaction boundaries for speed.
2. **First introduce test-only observability and reproduce baseline.** Count actual `DriverManager.getConnection` successes, physical initialization/schema guards, logical execute/query operations, pinned transaction acquisition/return, completed physical close; time phase medians, whole test cases and CPU (approximate where supportable). Opt-in diagnostics only, no secrets or permanent production logging. Include explicit `--rerun-tasks`/cache-state evidence, runner image/host class, JDK and exact SHA. Keep slow and concurrent tests intact; compare before and after on the same Windows runner class.
3. **Implement reuse only after audit evidence.** Use an explicit small bounded exclusive-lease lifecycle with no simultaneous access to one physical Connection. A transaction retains its own lease from BEGIN through COMMIT/ROLLBACK (including nesting) and is not returned between statements. Nontransaction queries/executeQuery must hold lease until ResultSet/Statement/mapper and callbacks finish. Distinguish `getConnection` physical creation from lease acquisition and `closeConnection` return; preserve SQLDelight's own thread-local management. Handle exhaustion/waits, interruption/errors, and prevent deadlock with nested transactions. Do not let an operation borrow a connection after closing begins. Avoid stale connection reuse after failed native operations or on dirty/uncertain transaction state.
4. **Guard each physical open exactly once before first use**: copy/scrub sensitive input in accordance with pinned library behavior; execute `PRAGMA busy_timeout=5000`, `PRAGMA foreign_keys=ON` and readback, `PRAGMA cipher_version` and encrypted-schema SELECT guard. Wrong key, damaged/tampered DB or configuration failure must fail closed; never add an unverified connection to the pool. Never log key material, credentials, database content or private paths. No persistent cache of key snapshots; securely clear driver-owned key when it can no longer be used. In failure close physical handles and wipe transient copies.
5. **Define a deterministic terminal close lifecycle.** Mark driver CLOSED so no new leases/opens can start, coordinate outstanding physical opens and in-flight leases/transactions/writers, drain without racing a used connection, actually close every native physical handle, then wipe owned key. Make close idempotent; after close every DB action fails. Document if special-cased timeout/interruption policy is necessary; never leave orphaned handles or an unbounded silent wait.
6. **Prove hostile and real concurrency cases on native encrypted Windows**: wrong key/tamper with unchanged file; encrypted header; multiple drivers; parallel readers and competing writers with exactly one CAS winner; foreign-key enforcement on every physical connection; nested success and forced rollback; RETURNING, no-row RETURNING, DML-without-RETURNING rejection; user_version migration atomicity; SQLITE_BUSY timeout/locks (no automatic retry of possibly executed DML); clean reopen after close; WAL, encrypted backup/restore portable copy; shutdown with in-flight writes/queries; exception or cancellation during statement/binding/mapping; ensuring no stale cross-thread transaction context; bounded connection count, unique lease ownership and cleanup of native files/directories. Preserve existing assertions; add independent deterministic tests rather than sleeps whenever feasible.
7. **Compare and report.** Isolated `SqlCipherWindowsConnectionProfileTest`, `PriceCatalogWindowsCipherTest`, `MixedDetailsSceneTest`, full Windows `:shared:jvmTest` + `:desktopApp:test` with actual uncached executions; include physical open count before/after, real encrypted guard count, per-phase medians, total class times, process CPU if available, total Windows suite and caveats. The Desktop scene may have independent bottlenecks; do not promise its entire time will disappear. Required FULL Android + Windows/iOS on the **same final head SHA** and independent code review before owner-only approval/merge. A critical shared DB change must continue to route CI to FULL, not advisory FAST/TARGETED.
