# CMP «Об’єкти та клієнти» — робочий план після PR #55

**Статус: UX бачення власника записане 01.11.2026, пропозиції обговорюються; фінальний дизайн/статуси/поля ще не затверджені.**  
**Гілка:** `feature/cmp-objects-clients` → `main`.  
**Issue:** [#58](https://github.com/aleks-nl5/andrey-ceilings-android/issues/58); вкладені маршрути — [#57](https://github.com/aleks-nl5/andrey-ceilings-android/issues/57).

## Навіщо етап

Перенести реальну роботу з об’єктами й клієнтами з Android-only Compose у `shared/commonMain` на Compose Multiplatform. Не копіювати стару верстку механічно: перед реалізацією власник хоче скоригувати вигляд екрана та робочу логіку. На час погодження дизайн-специфікації виконувати лише безпечний аналіз/підготовку спільних контрактів.

## Фактична база станом на 01.11.2026

- `app/src/main/java/com/andreyceilings/app/ui/screens/ObjectsScreen.kt` — Android-only `ObjectsScreen`, діалоги нового клієнта та об’єкта; справжні списки, створення, видалення, зміна статусу об’єкта.
- `shared/src/commonMain/kotlin/com/andreyceilings/shared/db/BusinessRepositories.kt` — справжні `ClientRepository` / `ProjectRepository`, CRUD, Flow, SQLDelight, UUID/soft-delete; не дублювати в новому presenter/store.
- `shared/src/commonMain/kotlin/com/andreyceilings/shared/domain/DomainModels.kt` — платформно-незалежні моделі/валідація; перевірити актуальність за реальною SQLDelight-моделлю, не множити моделі без потреби.
- `shared/src/commonMain/kotlin/com/andreyceilings/shared/navigation/AppNavigationState.kt` — маршрути й back stack, об’єднано в PR #55.
- `shared/src/commonMain/kotlin/com/andreyceilings/shared/prices/PriceCatalogScreen.kt` / `PriceCatalogStore.kt` — перевірений CMP-підхід до UI, що працює з реальним зашифрованим сховищем.

## Рішення, які маємо узгодити **до фінального CMP UI**

- Як організувати клієнтів і об’єкти: один список чи окремі вкладки/фільтри; який вигляд картки; яку інформацію показувати спочатку.
- Які дії/редагування потрібні під час першого CMP етапу: лише наявні чи нові; правила пов’язаних клієнтів та об’єктів.
- Як відкривати картку конкретного об’єкта, переходити до замірів/кошторисів та повертатися Back.
- Пошук, статуси, порядок сортування, порожні стани, попередження перед видаленням, дії на вузьких екранах і desktop.
- Затвердити чіткий MVP. Будь-які нові функції, що змінюють схему БД або бізнес-інваріанти, обговорити і винести за потреби в окремі issues.

**До цих рішень не затверджувати нову верстку і не оголошувати редагування/деталі реалізованими.**

## Архітектурний план виконання

1. Узгодити UX і сценарії з власником; оновити acceptance checklist #58.
2. Сформувати в `commonMain` мінімальний UI-state і команди для потрібних дій, підключивши **існуючі** `ClientRepository` / `ProjectRepository` та Flow. Валідація, помилки, `loading/empty/unavailable` — спільні; жодного Android Context у домені.
3. Реалізувати обраний CMP UI з одним набором компонентів для мобільного та desktop, без mock-даних; зберегти узгоджену графітово-бірюзову тему й читабельність.
4. Android `AppRoot` підключає спільний екран до реальної SQLCipher/SQLDelight сесії; існуючі швидкі дії працюють один раз і не повторюються після restore.
5. Windows host підключає до реальної зашифрованої БД лише робочі destinations; iOS спільний код компілюється та тестується, але runnable host/Keychain залишаються за #42.
6. Якщо затверджена UX-модель має деталі об’єкта, реалізувати мінімальні типізовані ID маршрути за #57. ID — лише посилання, не приватний запис; після process death і при недоступній БД safe fallback. Predictive Back повний preview — #56, не блокувати перший зріз.
7. Прибрати стару Android-only верстку **тільки після** функціонального паритету та тестування, без подвійних діючих джерел стану.

## Погоджуємо UX — нова концепція від власника (01.11.2026; робочий проєкт)

### Загальна композиція
- [ ] Дві вкладки «Об’єкти» / «Клієнти», початкова вкладка **«Об’єкти»**.
- [ ] ОДНЕ поле локального повнотекстового пошуку під вкладками, актуальне для обох типів записів незалежно від активної вкладки; підказки зі згрупованими результатами «Клієнти» / «Об’єкти», натискання результату відкриває конкретний запис без зайвого перемикання.
- [ ] Пошук за основними заповненими полями: назва об’єкта, адреса, статус, нотатки, ім'я клієнта, телефон (нормалізований), email; «Х» для очищення; не передавати пошукові дані на зовнішній сервер. Фільтрація поточної вкладки і глобальні підказки не повинні суперечити одна одній.
- [ ] Контекстна кругла FAB «+» праворуч унизу: створити об'єкт/клієнта за активною вкладкою. При прокрутці вниз плавно приховувати, при прокрутці вгору / зупинці — повертати повний розмір. Не перекривати системну навігацію, нижній CMP bar, клавіатуру чи поля.
- [ ] Mobile: свайпи; desktop: еквівалентні видимі дії/hover/context menu/keyboard, без залежності від жестів. Обидві теми та accessibility.

### Вкладка «Об’єкти»
- [ ] Горизонтальний ряд швидких chip-фільтрів за статусом: «Усі», «Замір», «Погодження», «Оплачено», «Монтаж», «Здано», «Скасовано», «Доопрацювання» та узгоджені додаткові.
- [ ] Лаконічні картки: кольорова позначка + **текст** статусу (не колір як єдина ознака); назва, адреса, за потреби клієнт, майбутня/остання подія лише з достовірних даних. Назву/клієнта/події власник позначив як відкриті рішення.
- [ ] Тап на картку відкриває редагування конкретного об’єкта (у формі чи nested screen — уточнити); Back зберігає контекст списку й пошуку.
- [ ] Свайп **ліворуч**: швидка навігація до адреси Google Maps / Waze, без автоматичного запуску зовнішніх застосунків без явного натискання дії; без адреси дія недоступна.
- [ ] Свайп **праворуч**: видалення **після підтвердження**. Обов'язково пояснити залежні заміри/кошториси; без випадкового безповоротного видалення.

### Вкладка «Клієнти»
- [ ] Лаконічні картки: ім’я, число пов’язаних **активних** об’єктів, телефон, адреса **лише якщо визначена семантика**.
- [ ] Натискання номера відкриває застосунок набору номера із заповненим номером, не здійснює дзвінок без підтвердження.
- [ ] Тап на картку — редагування клієнта; свайп ліворуч — швидкі дії Telegram / WhatsApp / Viber (або кнопки на картці, власник ще вагається), свайп праворуч — видалення з підтвердженням.
- [ ] Зовнішні месенджери — лише через безпечні platform adapters; врахувати відсутність застосунку, формат номера, Telegram privacy / username. Без відправлення повідомлень самим застосунком.

### Факти, які впливають на UX (перевірено у SQLDelight)
- Зараз `clients` має `name, phone, email, notes`, **не має окремого `address`**. Адреса є у `projects`; один клієнт може мати кілька об’єктів з різними адресами. Не приписувати клієнту випадкову адресу першого об’єкта. Варіанти: не виводити адресу в списку клієнтів; показувати основний об’єкт; або додати узгоджене поле «адреса клієнта» окремою контрольованою міграцією.
- `projects.status` — **одне** поле. Зараз Android мапить `measurement, calculation, approved, in_progress, completed, paid, cancelled`. «Доопрацювання» й окремий стан оплати в схемі ще відсутні.
- Реальні події з датами/часом **не зберігаються** у робочій таблиці подій, це майбутня #49. Не показувати `createdAt` або `updatedAt` як «наступний монтаж/замір».
- Видалення клієнта зараз soft-delete клієнта без автоматичного видалення його об’єктів; видалення об'єкта має залежні ефекти для кошторисів. Перед новими свайп-діями узгодити зрозумілу політику зв’язків/попередження.

### Рекомендовані поліпшення на обговорення (**не затверджено**)
- [ ] Розділити **етап виконання** і **стан оплати** (об’єкт може бути «В монтажі» та «Оплачено» одночасно) із контрольованою SQLDelight schema migration, якщо власник погодить; показувати два короткі індикатори і незалежні фільтри. До рішення не змінювати БД.
- [ ] Не захаращувати картку: назва й адреса — основні; ім’я клієнта — компактний підпис, подія лише за реальної #49; статус — кольоровий chip/пташка **з текстом**.
- [ ] Пошук/фільтри утримувати на екрані з розумним sticky-поведінкою; debounce і обмежені підказки, повага до IME/фокусу; SQLDelight local LIKE або FTS лише за доведеної потреби.
- [ ] Замість постійних кнопок месенджерів у списку — свайп-меню/контекстне меню; на Windows явна кнопка дій. Функції без потрібного номеру/username приховувати чи робити недоступними.
- [ ] Свайпи не повинні запускати небезпечну операцію одним рухом; правий свайп тільки відкриває підтвердження; швидкі дії не повинні конфліктувати з горизонтальними chip-фільтрами чи системним back gesture.
