Далі — P4B CMP UX і P4C нове immutable estimate save, кожен окремо. Після них UX [#95](https://github.com/aleks-nl5/andrey-ceilings-android/issues/95).

## 0. Погоджена бізнес-модель: незалежні та вибірково об'єднані кошториси (варіант C)

**Рішення власника:** створювати кошториси **окремо**, **одразу для всього об'єкта**, або формувати **вибірковий загальний кошторис**, самостійно позначаючи, *які вже створені кошториси включити, а які ні*. Вибір може охоплювати одну, декілька або всі стелі, але **одна стеля не дорівнює одному обов'язковому кошторису**: для стелі можуть існувати окремі альтернативні/додаткові документи. Структура має підтримувати довільну кількість стель і кошторисів на проєкт, без обов'язкового спільного документа. Об'єднання не видаляє, не редагує, не перенумеровує і не «поглинає» вихідні кошториси.

### Відокремлені рівні, без дублювання обчислювального ядра
1. **Розрахунок стелі** — pure `CeilingPricingInput -> CeilingPricingPreview` з явно обраними прайсовими позиціями, `measurementUuid`, рядками та вартістю; працює як зі збереженим валідованим заміром, так і з **валідованою незбереженою чернеткою** `MeasurementEditModel`. Модель розрахунку не володіє БД і нічого не записує.
2. **Кошторис-документ** (P4C) — окрема нумерована `estimate_series` з immutable revision; може містити одну стелю, декілька стель або лише окремий погоджений пакет робіт. Розрахунок стелі — не документ, а джерело його рядків.
3. **Вибіркова композиція на рівні об'єкта** — pure `ProjectEstimateSelection -> ProjectPricingPreview`: користувач задає явний впорядкований набір джерел (нові live ceiling previews і/або **конкретні існуючі immutable estimate revisions**, якщо їх власність та склад верифіковані), а також окремі необов'язкові project-wide роботи (наприклад доставка). Жодного правила «включати автоматично всі кошториси». Включення/виключення змінює лише зведений preview, **не** джерельні кошториси.

### Контракт вибору
- Кожен вибір однозначно ідентифікується: новий розрахунок — `projectUuid + measurementUuid + draft/sourceSignature + scope`; існуючий кошторис — `seriesUuid + explicitly chosen revisionUuid`, належність до того самого project перевірена. Не посилатися на «поточну останню» ревізію без фіксації UUID: її зміна не може тихо переписати зведення.
- Позначення лише потрібних джерел: кухня+коридор, усі стелі або будь-яка інша комбінація. **Тотал = сума тільки включених рядків/секцій + явно включених загальнооб'єктних робіт**; виключені залишаються доступними окремо, але не впливають на суму.
- При виборі existing revision використовується **її заморожена ціна/кількість** як документальна пропозиція, без таємного перепрайсування поточним прайсом. При створенні нового live розрахунку — чинна перевірена ціна прайсу. Змішане походження рядків має бути явно відображене й збережене у майбутньому aggregate snapshot.
- Один source revision не можна включити двічі. Якщо два вибрані кошториси перекривають одні й ті ж роботи/елементи, за доступною provenance сигналізувати overlap; **не робити приховане подвійне нарахування або автоматичне віднімання**. Без достовірної деталізації старого кошторису — явний `AMBIGUOUS_COVERAGE` / `PROVENANCE_MISSING`; рішення про склад/розділення — в UX P4B/P4C, а не евристика за назвою.
- Одні й ті ж `measurementUuid` можуть бути присутні в різних самостійних документах, якщо це різні явно означені роботи; **сам факт однакової стелі не означає дублікат**. Збіг provenance конкретного рядка/елемента є підставою для перевірки.
- Не допускати рекурсивного включення зведених кошторисів без окремо спроєктованого механізму flatten/cycle detection. P4A може приймати лише перевірені **листові** джерела/ревізії; складні старі чи зведені джерела з невідомим складом блокуються.
- P4A реалізує **тільки типи, чисте вибіркове агрегування та read-only preview/валидацію** (жодного збереження списку вибору в БД). Вибір галочками та режими створення — P4B; фіксація *нового* окремого/вибіркового/загального документа з усіма включеними frozen row snapshots та exact revision refs — P4C.
- Нові commonTest: 1/4/усі стелі, довільна підмножина існуючих revision UUID, об'єктні роботи один раз, невибрані не впливають на суму, зміна live прайсу не переписує frozen revisions, дублі source/provenance, missing/deleted/cross-project revision, stale draft/signature, порядок/ідемпотентність, aggregate cents = точна сума source lines.

**Окреме рішення на майбутнє:** чи дозволяємо змішувати у *одному зведенні* frozen старі кошториси та нові live-розрахунки. Контракт дає можливість показати обидва з явно різним походженням, але фінальну UX-політику підтвердження фіксуємо до реалізації P4B/P4C.

## 0.1. Політика збереження: у БД тільки свідомо зафіксовані кошториси (погоджено)

**Рішення власника:** динамічні окремі та зведені розрахунки — **епізодичні чернетки у пам'яті**, а не записи `estimates`/`estimate_series`/`estimate_revisions`. У БД кошторис з'являється **лише після явної дії «Зберегти» або підтвердженої користувачем дії «Зберегти та друкувати» / фіналізувати для PDF-експорту**. Перегляд, зміна параметрів, вибір або виключення стель/кошторисів, повторне обчислення, відкриття preview/PDF preview, перехід між варіантами і скасування **не створюють** кошторисних записів, навіть тимчасових. Автозбереження чернеток у production SQLCipher/SQLite не допускається.

- **Сесійний `EstimateCompositionDraft` (P4B):** UI тримає у пам'яті явний вибір source revision UUID/live ceiling source, project-wide роботи, змінені кількості/ціни за дозволеними правилами та read-only preview. Він не має номера документа, `seriesUuid`, `revisionUuid`, рядків історії чи запису в БД. Зміни в прайсі або вихідних даних перевалідовуються; незбережена чернетка може загубитися після примусового завершення застосунку — це усвідомлений наслідок відсутності запису в БД. Стан збережених **замірів і прайсу** працює за чинними правилами; політика стосується саме кошторисів.
- **`Preview` / перегляд майбутнього PDF:** без жодного запису кошторису. Дозволено суто ephemeral render in memory або тимчасовий файл у cache, який не стає документом/backup і чиститься. Показувати «Попередній розрахунок», **не** резервувати номер документа наперед.
- **`Зберегти` (P4C):** одна явна операція, яка в *одній SQLDelight транзакції* повторно перевіряє price/catalog + measurement and selected revisions/source signatures, заморожує всі включені секції/рядки/ціни/кількості/provenance, виділяє унікальний номер і вставляє новий immutable series v1 або явно підтверджену нову revision. При validation failure, cancel до commit або SQLCipher failure — **0 кошторисних записів і 0 витрачених номерів**; не зберігати частину зведення.
- **`Зберегти та друкувати` / фінальний PDF-експорт (P4C):** спершу користувач підтверджує остаточний склад документа; потім **збереження snapshot**, і лише з цього самого зафіксованого snapshot генерація/відкриття PDF для системного друку/передачі. Не друкувати кінцевий документ з незбережених live-даних, щоб екземпляр PDF не розходився з БД. Якщо print/share після commit не вдався або OS dialog закрили, уже свідомо збережений кошторис залишається у БД, а повторний друк бере **ту саму ревізію** без створення дубліката. ОС може не підтвердити фізичний вихід паперу; факт відправлення на системний друк **не** означає `physically_printed=true`.
- **Повторне відкриття та друк без змін:** береться раніше збережена immutable revision, **без нового номера/кошторису/ревізії**. Зміни вже збереженого кошторису залишаються ephemeral до окремого підтвердження **«Зберегти нову ревізію»**; не модифікувати історичні дані на місці. Приклад: чотири live room drafts і довільні підмножини не створюють таблиць історії; тільки обраний і явно збережений вибірковий документ стає новою series.
- **Захист від подвійного натискання, crash, retry:** одна підтверджена фіналізація — один persisted immutable результат; в ідеалі передати stable operation UUID/idempotency у P4C, синхронізувати з existing immutable series/journal patterns, не створювати дублікати після втраченої відповіді. Обидві межі `DB commit` і зовнішній системний print/OS callback незалежні; не можна обіцяти атомарний physical print.
- **Тести:** 100 перемикань складу, редагування preview, його скасування, PDF preview -> **0 rows / 0 series numbers**; явне Save -> рівно один immutable snapshot; failed validation/concurrency/SQLCipher crash before commit -> rollback; підтверджений print з відмовою printer/open/share і повторною спробою -> жодних дублів; reprint old revision -> 0 нових revision; після успішного Save історія не реагує на зміну прайсу; вибірковий aggregate лише обраних source revisions.

**Розмежування етапів:** у P4A реалізувати лише read-only pure models/preview/selection API, **без writer**; P4B — сесійна незбережена UX-чернетка; **тільки P4C** — атомарна фіналізація (збереження/друк) і immutable snapshot. Не вводити таблицю `draft_estimates` чи «вічний» autosave, не вимагати від P4A зміни схеми v14.

## 0.2. Погоджені та потенційні роботи — окремі підсумки (варіант B; 06.11.2026)

**Рішення власника:** живий KMP-калькулятор завжди відображає **погоджену вартість** і **окрему можливу вартість непогоджених робіт**. Непогоджене не включається автоматично в основну суму, зведений кошторис, PDF або збережену ревізію. Для P4A це **два відокремлені pricing buckets** одного pure preview, а не два незалежні кошториси, дубльовані записи чи нові таблиці.

- **`CONFIRMED` / погоджено:** `ElementApproval.APPROVED` або окремі базові позиції, **явно підтверджені для розрахунку**; тільки при валідованій кількості, сумісній одиниці та підтвердженій актуальній ціні. Такий рядок рахується у `confirmedTotalCents` рівно один раз. Підтверджене, але `Unknown`/`Range`, без ціни, з конфліктом або без підтвердження необхідних геометричних даних — **блокер**, а не мовчазне заниження основної суми до нуля.
- **`POTENTIAL` / обговорюється:** `ElementApproval.DISCUSSING` із валідною ціною, сумісною одиницею та **однозначною кількістю** (`Exact` або дозволена `CeilingArea`/`CeilingPerimeter` за validated geometry). Його вартість відображається **в окремому `potentialTotalCents`** з посиланням на `measurementElementUuid`, без впливу на `confirmedTotalCents`, без автоматичного включення у майбутню immutable ревізію.
- **Неоцінюване/неоднозначне:** `Wish` без явної каталожної прив'язки, `Unknown`, `Range`, несумісна одиниця, видалений item/group, відсутня ціна, невиміряна геометрія, stale identity — окремі `unpricedOrNeedsInput` / typed problems; **не підставляти нуль чи середину діапазону**. Для `Range` можна вивести інтервал лише як необов'язкову окрему аналітику, але **не** додавати діапазон у скалярний `potentialTotalCents`. Якщо є непрораховані потенційні роботи, показувати `potentialIncomplete = true` і **не** подавати потенційну суму як повну максимальну ціну.
- **`total` без подвійного сенсу:** `confirmedTotalCents` = тільки погоджені, `potentialTotalCents` = тільки кількісно визначені непогоджені, `possibleCombinedTotalCents` за потреби = їхня арифметична сума, **явно позначена як умовний сценарій, а не фінальна вартість**. `potentialIncomplete` не дозволяє трактувати її як повну ціну всіх побажань. Source UUID та price identity залишаються у кожному рядку; одна робота не може бути одночасно в обох групах.
- **Об'єктний рівень:** вибіркове агрегування додає окремо confirmed→confirmed і potential→potential тільки для явно включених стель/складових; project-wide роботи мають ту саму класифікацію. Історичні frozen estimate revision lines залишаються зафіксованими документальними рядками, їх **не класифікувати як непогоджені заново** лише через поточний статус елемента. Не переносити potential у confirmed через включення джерела у зведення.
- **Фіналізація в P4C:** потенційні позиції можуть потрапити в майбутній збережений кошторис **лише після явного рішення користувача** та необхідної перевірки/підтвердження цих позицій у P4B. Не змінювати автоматично `ElementApproval` у БД. Базове «Зберегти» не включає `DISCUSSING` непомітно. Жодних записів кошторису під час перемикання approval/preview.
- **Тести P4A:** approved 6 шт. vs discussing 2 шт.; однакова ціна/тип, різні element UUID; 6 маркерів або лише 4 не змінюють задекларовані погоджені 6; comparing exact vs Unknown/Range; deleted/changed price; potentialIncomplete; окреме округлення кожного рядка; `confirmedTotalCents` інваріантний до змін тільки потенційних; selection subset; нуль duplicate across buckets; no estimate writes.

**Межі:** бізнес-класифікація і pure sum у P4A, UI двох підсумків і confirmation controls у P4B, immutable Save/Print policy в P4C. Це **не змінює** рішення про transient drafts, persist-on-confirm та історичні кошториси.

## 0.3. Самостійні кошториси замість окремого механізму «альтернативних пропозицій» (рішення власника)

**На ранньому етапі не реалізовувати окремий тип/конструктор альтернативних комерційних пропозицій.** Достатньо можливості формувати **декілька незалежних кошторисів** для одного об'єкта та навіть тієї самої стелі; кожен зберігається як власна immutable series/revision за погодженим правилом persist-on-confirm. Вони можуть відрізнятися моментом створення, набором включених стель/робіт, актуальними цінами на момент явної фіналізації та/або дозволеними свідомими змінами в тимчасовій чернетці. Ніяких автоматичних «варіант A/B», копіювання записів чи прихованого створення документів під час preview.

**Окремий робочий статус кошторису, подібно до статусу об'єкта:** передбачити можливість зберігати workflow/status metadata на рівні **кошторисного документа (series)**, **незалежно** від `ElementApproval` елементів заміру і від статусу самого об'єкта. Статус документа не змінює його frozen revision, фінансові рядки, суму, номер чи PDF, і **не підтверджує автоматично роботи в замірі**. Для нового статусу потрібен окремий versioned/CAS metadata-update boundary у P4C/подальшому етапі, з урахуванням наявної фізичної схеми; **не додавати статус/DDL та міграцію у read-only P4A**. Набір статусів, підписи й назви кнопок визначимо на пізнішому UX-етапі, зараз жодного hard-coded UI enum на припущеннях.

**Не дублювати вибір робіт у калькуляторі.** Для елементів, які користувач **вже додав до заміру та прив'язав до каталогу**, pure P4A calculator бере наявні `MeasurementElement` (UUID, source, approval, quantity) та ціну з активного прайсу автоматично: `APPROVED` → confirmed, `DISCUSSING` → potential, якщо кількість і ціна валідні. **Немає додаткової дії «включити елемент у калькулятор»** і немає другого editable переліку тих самих елементів. Фізичні `POINT/LINE/AREA` placements залишаються джерелом перевірки, а не додатковими фінансовими рядками. Лише те, **чого немає у замірі як однозначно вибраної каталожної позиції**, потребує окремого explicit selection (наприклад базове полотно/профіль, project-level доставка, manual work); не робити автоматичний fuzzy match або synthetic default price.

**Створення іншого кошторису ≠ зміна статусу в замірі.** Різні окремо фіналізовані документи не редагують `MeasurementElement.approval` і не модифікують інші документи. P4B може мати явний transient вибір вже прорахованих складових **при складанні конкретного документа**, але це не повторний додаток елемента до заміру і не частина read-only P4A. Погоджена сума і potential сумуються окремо й надалі.

**Тести/acceptance:** один замір → два різні явно збережені кошториси з власним UUID та номером; зміна статусу першого не змінює статус другого, не створює нової immutable ревізії й не впливає на замір; кілька preview без Save → жодної серії; `APPROVED`/`DISCUSSING` з валідними catalog links присутні у відповідних bucket **без додаткової дії вибору**; немає double count при repeated read/placement; статус і labels UX не імплементовані у P4A.

## 0.4. Замір як повна технічна модель робіт; типові набори — пізніше (рішення власника)

**Канонічне призначення заміру:** зафіксувати **все відоме про майбутню роботу майстра** — контур і розміри, полотно/матеріали, профілі, освітлення, ніші, інші роботи/побажання, розміщення, фізичні й заявлені кількості та погодження. **Замір задає «що робимо», прайс — «скільки коштує», P4A калькулятор лише співставляє вже описані роботи з чинною ціною.** Відсутня позиція у замірі не повинна тихо створюватися або підставлятися калькулятором. Незбережена розрахункова чернетка лишається без estimate writes; збережені заміри та catalog records використовують існуючу БД.

- **Єдина модель позиції в замірі:** основні матеріали, як полотно чи профіль, — такі самі typed `MeasurementElement` з `ElementSource.CatalogSelection(priceItemUuid, code, quantityMode, placementKind)`, що і додаткові роботи. Вони **не** зобов'язані мати Canvas `POINT/LINE/AREA` placement: `PlacementKind.NONE` — допустима бізнес-позиція без геометричного маркера. `CEILING_AREA` та `CEILING_PERIMETER` беруть кількість із validated captured geometry за своїми правилами, `MANUAL`/`ENTERED_LENGTH` — тільки визначену declared quantity. Не створювати окремі hardcoded `canvasPrice`/`profilePrice` правила чи другий список базових кошторисних selections у калькуляторі.
- **Read boundary має охоплювати ВСІ активні елементи заміру**, включно з unplaced, `PlacementKind.NONE`, `Wish`, approved/discussing і поза списками LINE/AREA/POINT. Поточний `MeasurementEditDocument` (у P3C5) містить мапу версій/overlay-елементи, але не обов'язково повний матеріальний список для фінансів; P4A adapter має читати `MeasurementElementRepository` для конкретного `measurementUuid` **в межах одного узгодженого DB snapshot** разом із контуром, placements, прайсом і child/version token. Не обрізати pricing на елементах із маркерами.
- **Кілька полотен/профілів та часткові ділянки:** ядро **не припускає**, що полотно чи профіль тільки один, або що будь-яка позиція обов'язкова в кожному замірі. Розрахунок залежить від введеного `QuantityMode` та заявленої кількості. Коли на одній стелі частина полотна/периметра потребує іншого матеріалу/профілю, не застосовувати повну `CeilingArea`/`CeilingPerimeter` **кожній** позиції: потрібна явно задана часткова кількість, а її сумісність з каталожним режимом має бути перевірена. Якщо чинна модель каталогу не дозволяє коректно поділити метри для певного mode, fail-closed/needs-input до явного коректного моделювання; **ніякого автоматичного подвоєння площі чи периметра**. Не реалізовувати неузгоджений geometry solver.
- **Склад неповний:** якщо користувач ще не зафіксував полотно/профіль чи деякі інші роботи, калькулятор не вигадує їх і не бере defaultPriceList. Статус неповного складу/потенційної ціни можна показувати як діагностику; **не встановлювати універсальні hardcoded обов'язкові позиції** без окремого рішення. Прайсові `Wish` без selection залишаються поза фінансовими підсумками до вирішення.
- **Типові набори і розширений довідник** потрібні як майбутній спосіб швидко наповнювати замір стандартними матеріалами та побутовими/додатковими роботами. **Свідомо відкласти до працездатної базової версії застосунку.** Сьогодні закладаємо лише сумісний універсальний element/quantity/source контракт, без нових seed rows, preset UI, автоматичного додавання шаблонів, додаткових таблиць, міграцій або розширення price items у P4A. Можливість у майбутньому редагувати набори й довільно розширювати каталог не повинна вимагати переписування ядра.
- **Acceptance:** один `PlacementKind.NONE` canvas (`CEILING_AREA`) + один profile (`CEILING_PERIMETER`) + POINT/LINE/AREA, усі з одного валідованого заміру → один preview, без повторного вибору; кілька різних профілів без подвоєння за замовчуванням; missing base items → no synthetic lines; Wish/unknown/invalid → typed issues; all-unplaced element rows included by coherent read; жодних estimate writes чи schema changes.

## 1. Мета і межі
Побудувати **одне детерміноване ядро read-only розрахунку в shared/commonMain**: валідований замір/контур + **повний набір measurement-owned `MeasurementElement`** (у тому числі `PlacementKind.NONE` без маркера) + POINT/LINE/AREA як геометричні відомості + активний прайс → перевірений, пояснюваний **живий preview майбутнього кошторису** (рядки, ціни, кількості, тотали, попередження, блокери, версії). Не створювати паралельний калькулятор, дубль прайсу чи Android-only правила. Результат — API для майбутнього CMP P4B та P4C, **не** новий кошторис або PDF вже в P4A.

**Поза scope P4A:** нові Compose екрани/UX, редагування/переміщення Canvas, збереження draft кошторису, створення серії/ревізії, PDF, масове перепрайсування, зміна існуючих цін, геометричний solver #70, SQLCipher migrations без доведеної потреби, повноцінний iOS host #42. Не вмикати автоматичне pricing історичних кошторисів.

## 2. Чинна архітектура, яку обов'язково повторно перевірити
- `measurement/MeasurementElement.kt`: `ElementSource.Wish` або `CatalogSelection(priceItemUuid,code,quantityMode,placementKind,availability)` **без sale price**; `ElementQuantity.Unknown/Exact(milli)/Range/CeilingArea/CeilingPerimeter`, approval, placement і placedQuantity незалежні.
- `measurement/MeasurementEditStore.kt` / `db/CeilingEditRepository.kt`: єдиний coherent measurement document та journal/CAS для contour+POINT+LINE+AREA; child-only зміни можуть не збільшувати `room_measurements.updatedAt`.
- `measurement/MeasurementGeometryCodec.kt`, `estimate/FrozenPolygonGeometry.kt`, `calculation/KmpCeilingCalculator.kt`: verified captured geometry, зафіксована точність, KMP geometry. Не створювати фіктивну точність для historical shapes.
- `prices/PriceCatalogModel.kt`, `prices/PriceCatalogStore.kt`, `db/BusinessRepositories.kt`: активні `price_items` + активні `price_groups`, UUID, immutable semantic code, unit, quantityMode, placementKind, sale price, updatedAt, soft delete.
- `estimate/ImmutableEstimateRepository.kt`, `estimate/EstimateRecalculationRepository.kt`: історичні серії/ревізії, snapshots і reprice previews **не** є P4A writer. Не змінювати public history semantics або `kmp-v1` golden vectors.
- Перед реалізацією прочитати `AGENTS.md`, roadmap, issue #44, поточні схеми `BusinessSchema.sq` та migration v14; орієнтуватися на *фактичний* main, не на застарілі архівні зрізи.

## 3. Домени і API
Проєктовані назви (можна адаптувати до існуючого стилю, але семантика незмінна):
- `LiveEstimateSource`: project/measurement UUID, captured geometry + precision, coherent document (усі активні measurement elements, у т.ч. NONE/unplaced та Wishes; point/line/area overlays, version set/receipt). Полотно/профіль і будь-які інші роботи вже описані як catalog-linked елементи заміру; **ніякого окремого повторного списку базових selections у калькуляторі**; жодного fuzzy-підбору за назвою чи позицією у прайсі.
- `ActiveCatalogSnapshot`: лише активні catalog items з активними групами, UUID, code, unit, quantityMode, placementKind, salePrice, updatedAt, group UUID/version.
- `LiveEstimateLine`: stable source key (`element:<measurementElementUuid>` для всіх measurement items; окремий scope тільки для явно доданих project-wide робіт), measurementUuid, optional elementUuid, catalogItemUuid, stableCode, title, normalized unit, quantityMilli, unitPriceCents, totalCents, quantityOrigin (`CAPTURED_AREA`, `CAPTURED_PERIMETER`, `DECLARED_EXACT`, `EXPLICIT_BASE`), review flags. Жодного dependence від Canvas pixel координат.
- `LiveEstimatePreview`: sorted deterministic lines + blockers/warnings, totalCents, `canConfirm` як майбутня capability (у P4A **ніколи** не викликати save), source signature / catalog token для майбутнього транзакційного recheck. Typed failure states (parent unavailable, invalid geometry, price not found, catalog metadata drift, incompatible unit, ambiguous quantity, stale/coherent read failure, overflow, DB unavailable); жодного тихого $0 fallback.
- Pure `buildPreview(source, catalogSnapshot)` окремо від SQLDelight read adapter. Read adapter обов'язково бере **один узгоджений транзакційний зріз** measurement, children, catalog+groups та версійних токенів; не комбінувати незалежні hot Flows, що дають суміш станів. Після mutation повертати новий snapshot; стара чернетка або preview не стають «чинними» автоматично.

## 4. Правила кількості і ціни
1. **Тільки явно обраний каталог**: ідентичність за `priceItemUuid`, звірка code, unit, quantityMode, placementKind та активності item+group. Selection-time snapshot не містить ціни; для *нового* preview прочитати live sale price. Якщо позицію видалено/перенесено несумісно/змінено метадані — typed blocker, без rebinding за title або code, без позичених дефолтів.
2. **Основні матеріали такі ж самі елементи заміру:** полотно, профіль та інші роботи мають бути *явно зафіксовані у замірі* як `MeasurementElement.CatalogSelection`; calculator їх **не вибирає вдруге**. `PlacementKind.NONE` підтримує unplaced матеріали. `CEILING_AREA` → валідована площа у м², `CEILING_PERIMETER` → валідований периметр у м.п.; часткові кількості не можна безпідставно трактувати як повну площу/периметр. Відсутність полотна чи профілю — не привід створювати synthetic рядок/цінник, і не універсальний blocker для замірів із неповним/іншим складом робіт. Заборонено підставляти legacy `materialType` або `KmpCeilingCalculator.defaultPriceList()`.
3. **Measurement elements:** каталогові `APPROVED` з `Exact` і unit-compatible ціною формують максимум **один рядок на element UUID**, незалежно від числа фізичних placements. Для quantityMode `CEILING_AREA`/`CEILING_PERIMETER` — тільки відповідна derived quantity з captured geometry; `MANUAL`/`ENTERED_LENGTH` — лише явно підтверджена `Exact` з коректною одиницею (м.п. для entered length). `Wish`, `Unknown` та `Range` залишаються видимими як `NEEDS_INPUT/UNPRICED`, не перетворюються на нуль або середину діапазону; `DISCUSSING` з точною валідованою кількістю і ціною потрапляє **тільки в окремий potential bucket** згідно з §0.2. Вибір складових *документа* у P4B не є повторним вибором/додаванням елементів для калькулятора. Не допустити непомітного «готового» кошторису із пропущеними необхідними рядками.
4. **Placed vs declared:** `placedQuantityMilli`, фактичні point count/line length/area і `APPROXIMATE/EXACT` — контрольні величини та status/review, **не приховане джерело нової фінансової кількості**. Для LINE окремий measured length не переписує заявлену `Exact`; для AREA геометрична площа й declared quantity незалежні. Sticky unresolved/review є видимими; preview не вважається confirmable без явного усунення/погодження блокувальних станів майбутнім P4B.
5. **Annotations:** `AREA role=OBSTACLE/VOID_MARKER` без explicit compatible catalog element — лише позначки: **не віднімати** площу, не генерувати ціну, не змінювати периметр, не інтерпретувати отвір як 2D boolean cutout. Коди `light.*` тощо не створюють кошторисний рядок за самою назвою.
6. **Одиниці:** не змішувати `м²`, `м.п.`, `шт.`, `компл.`, `послуга` та custom units. Цілі `шт.`/комплекти — тільки за явно валідованими правилами; unsupported custom unit без явно визначеної семантики → blocker. Нульова **наявна** ціна продажу дозволена як справжнє 0, але missing/deleted/invalid не позначати нульовою.
7. **Математика:** quantity у canonical Long milli, sale price — перевірена кількість **копійок Long** (ціна у БД зараз REAL; convert only with strict 2-decimal cents check), підсумок рядка = half-away-from-zero round(cents × milli / 1000) **один раз за рядок**, total = точна сума цілих копійок. Guard на overflow, NaN, negative, overprecision; без `Double` для множення грошей і без неявного кількаразового округлення. Повага до зафіксованої geometry precision; не міняти її під час перерахунку.
8. **Детермінізм/ідемпотентність:** same validated source+catalog snapshot → byte-for-byte equivalent preview, stable line ordering/keys, без duplicate charge при повторному reload/Flow або overlapping POINT+LINE+AREA. Content token включає всі визначальні версії та зміни у child records, не лише parent `updatedAt`.

## 5. Persistence / concurrency
P4A read-only: **жодних INSERT/UPDATE у production tables, жодної schema v15**, якщо відсутня окремо доведена технічна потреба. Не торкатися SQLCipher key/WAL, restore/backup, receipts/tombstones, numbering, historical estimates/revisions/PDF. Для майбутнього P4C зберегти `sourceSignature`/catalog signature і контракт повторної перевірки **в одній DB write transaction** без TOCTOU; P4A не удає, що один лише token захищає майбутнє збереження. `ImmutableEstimateDraft`/`ImmutableEstimateLine` — тільки майбутнє адаптування на P4C без writer у цьому PR.
