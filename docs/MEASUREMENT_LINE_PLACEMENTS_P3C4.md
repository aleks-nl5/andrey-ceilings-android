## 1. Сценарій майстра, який треба завершити одним функціональним PR

У збереженій стелі «Кухня» користувач має catalog element `placementKind=LINE`, `unit=м.п.`, заявлена довжина `Exact(4500)` (4,5 м). У CMP «Елементи стелі» вибирає його → **«Розмістити»** → у спільному кресленні задає два кінці прямої лінії (спершу приблизно), бачить виділення/відрізок/довжину, потім **реальними монтажними відстанями від вибраних стін** точно фіксує обидва кінці. Може створити другу незалежну лінію **того самого елемента** (кожен сегмент має свій UUID), перемістити/відредагувати/видалити вибраний сегмент, змінити контур і побачити коректний preview. Одне Save зберігає **контур + усі точки P3C3 + лінійні зміни** атомарно, у normal/fullscreen; повторне відкриття, перезапуск, backup/restore зберігають ті самі UUID, стіни, кінці, відстані й статуси. **Точний довжинний результат обчислюється з геометрії автоматично.**

Лінії — це **окремий typed world-mm overlay** над контуром, не ребра контуру, не `drawingJson`, не точкові placements і не фінансові рядки. Перший вертикальний зріз — **прямолінійні сегменти** (по одному початку/кінцю на запис); кілька сегментів дозволяють складнішу конфігурацію без обіцянки повноцінного polyline/area CAD. Довільний напрямок самого сегмента можливий, навіть коли outline ортогональний; це **не** реалізація solver #70.

## 2. Спільна KMP доменна модель

- Створити типізований `LinePlacement`/геометричний `CeilingFeature` відповідної спеціалізації: stable `uuid`, `elementUuid` (FK/association до `MeasurementElement`), `start(xMm,yMm)`, `end(xMm,yMm)` як `Long`, опційна `widthMm` і примітка якщо доречно, precision/provenance, незалежні **endpoint anchors** із stable persistent `ceiling_walls.uuid`, version/timestamps/tombstone, `needsReview`/`unresolved`, geometry/last-valid context. Напрямок визначається двома кінцями, **не** зберігати ще один незалежний angle/length як другу істину. Не підміняти POINT schema чи UUID.
- Валідація: ненульовий сегмент, координатні bounds з чинної геометрії, мінімальна фізична роздільна здатність 1 мм; endpoints і **весь сегмент** повинні лежати у допустимій внутрішній області validated simple polygon. Самих валідних endpoints **недостатньо** для увігнутої L/U стелі: перетин вирізу, інших стін, вихід за контур/дотик до стіни відхиляти. У цьому вузькому етапі лінія є **центральною віссю/монтажною траєкторією**, а не геометричним вирізом; boundary-attached/width-envelope, що фактично виходить за контур, не оголошувати перевіреним отвором чи завершеним CAD, пояснити обмеження. `widthMm` не змінює площу.
- **Монтажний ввід:** для **кожного кінця** використати чинний physical `WallAnchor` з **двома перпендикулярними відстанями від вибраних стін**, fallback — `ALONG_INWARD` від однієї стіни. Використати/узагальнити solver P3C3, не дублювати математику й не тримати X/Y як основну форму майстра. Відстані — цілий mm; X/Y — детерміноване похідне округлення; перевірити finite-foot/visibility/concave/reversed/near-parallel/1-mm tolerance. Вільний drag кінця чи сегмента — **лише приблизний**, активні measured anchors цього зміненого кінця скидаються з видимим поясненням. Exact — лише коли **обидва кінці** мають збережені перевірені measured anchors, не через простий tap/drag.
- Зміна геометрії: за **доведено незмінних wall identities** відновити кожен anchored endpoint із тих самих відстаней; немає nearest-wall або AB-index rebinding. Для відповідного valid segment поставити durable `needsReview`, «Перевірити / Пізніше». Якщо хоча б одна опора втрачена/невалідна, або сегмент проходить поза новим contour, зберегти UUID, останні відомі координати й anchor/context, перевести **весь сегмент** у `unresolved`; не враховувати його як валідно розміщений. Розширення контуру або free drag **не знімають sticky unresolved**: потрібні нові допустимі measured anchors та явне підтвердження. Для unanchored legacy/approx segments не вигадувати measured dimensions.
- Визначити явні KMP typed failures/status, cleanup при видаленні element/measurement/parent та reactive Flow/ownership. Жодних cross-ceiling orphan records.

## 3. Довжини і кількість: важливий контракт

- Довжина **кожного збереженого валідного сегмента** = евклідова відстань між `Long` endpoints, **детерміновано округлена до 1 мм** одним KMP правилом із перевіркою безпечних bounds/overflow. Сума в мм = сума в `milli` для `м.п.` (`2.500 м` = `2500 milli`). Математика не залежить від zoom/pan, px, DPI, локалі; формат відображення підтримує кому/крапку, без Double як persisted quantity source.
- Для LINE використовувати `placedQuantityMilli` як **суму довжин тільки активних valid line segments**, окремо від заявленої `ElementQuantity`; `UNPLACED/APPROXIMATE/EXACT` показує реальну provenance валідних placements. Unresolved сегменти залишаються записаними й резервують свою останню відому додатну довжину для перевірки місткості, але **не** входять у valid placed quantity. Відображати «Заявлено 4,5 м · На кресленні 2,5 м · Потребує уточнення: 1 сегмент» замість мовчазного дописування заявленого.
- **Не переписувати заявлену довжину автоматично при drag або зміні контуру**: узгоджена політика — **довжина геометрії обчислюється й оновлюється автоматично**, а перехід від попередньої/ручної до розрахункової заявленої кількості має **явну дію «Взяти довжину з креслення»** з видимим preview і атомарним CAS. Це зберігає різницю «замовлено» / «розміщено», кількості ще не розміщених елементів та майбутню модель калькулятора #44. При `Unknown/Range` не підставляти непомітно maximum/mean як Exact. Дозволити ручне `Exact`/орієнтовну довжину **без Canvas**.
- Для заявленого `Exact` і (якщо застосовно) верхньої межі `Range` не перевищувати quantity активними+reserved segments без явного виправлення quantity в тому самому безпечному workflow; не зменшувати quantity нижче вже розміщеної/зарезервованої довжини. Якщо поточні правила `ElementPlacement`/`MeasurementElementRepository`/тригери розраховані лише на точки, **розширити discriminator за `placementKind`**; не ламати point capacity `1 шт.=1000 milli`, P3C3 unresolved reservations і POINT статуси.
- `Wish`, `NONE`, `POINT`, `AREA`, не-`м.п.` і неузгоджені quantity modes **не отримують LINE write**. Для `LINE + м.п.` допускається `ENTERED_LENGTH` та сумісний `MANUAL`; `CEILING_PERIMETER` не є розміщеною лінією. Пояснити неможливість, не виконувати неявних конвертацій. Редагування `placementKind` прайсу не переписує вже збережений `CatalogSelection` snapshot.

## 4. Один CMP Canvas та передбачувана взаємодія

- Додати малу зрозумілу дію **«Розмістити лінію»** лише для сумісного каталожного елемента. Після вибору елемента режим двох кінців: перший tap — початок, другий — кінець (локальна чернетка), preview/довжина, явне `Зберегти`/`Скасувати`. Не записувати half-segment або SQL на кожен tap/pixel.
- Тап по відрізку (із комфортним hit target незалежно від товщини лінії) виділяє **конкретний UUID** і пов'язаний item у розділі «Елементи стелі». Дії: перемістити обраний сегмент або окремий кінець, змінити дві монтажні прив'язки, optional width/note, видалити з підтвердженням, Undo/Redo, Fit/zoom/pan, normal/fullscreen. Не створювати другого Canvas, подвійного editor state або конкуренції жестів із POINT/wall selection. Pinch/pan/cancel/Back не мають створювати/переміщувати сегмент.
- На екрані «Редагувати замір» лінійні зміни **та точки/контур** в одному validated draft і **одному атомарному Save**. У fullscreen використовувати той самий model/gesture arbiter. Не робити тихих partial commits між контуром і placements. Dirty Back/route/rotation/IME, stale conflicts, невідомий результат commit, session close повинні поводитись як P3C3 (не губити чернетку, no untrusted auto-retry).
- Видимі стани: «Не розміщено», «Розміщено … м з … м», «Приблизно», «За виміряними відступами», «Перевірити (N)», «Потребує уточнення (N)». М’який, функціональний UX без глобального редизайну #95. Не вводити декоративні/фальшиві дані.

## 5. SQLDelight/SQLCipher і транзакційний захист

- **Актуальна schema v11 → v12** окремою новою additive migration (перевірити реальну версію на старті). Нова typed normalized `line_placements` (або чітко обґрунтоване еквівалентне рішення), FK/indexes/CHECKs/soft-delete, endpoint mounting/provenance/review metadata, CAS і ідемпотентні operation receipts. Не зберігати line overlay як ескіз у `drawingJson`, JSON можна використовувати лише для типізованого перевіреного mounting/immutable journal там, де це вже робить P3C3.
- **Особливо важливо:** P3C3 `CeilingEditRepository` і `ceiling_operations/results` атомарно обробляють контур, walls і **повний набір точок**. Розширити їхній повний набір на LINE з жорсткою транзакційною перевіркою version/ownership/complete set, safe remap, valid/unresolved/status, immutable receipt/result/actual versions. Не додавати окремий line Save, який дозволив би partial contour/point/line mutation; не залишати SQL bypass на безпосередній table UPDATE. Якщо існуючі `point_contour_guard`/summary triggers мають змінитися, не послаблювати захист P3C3, довести tests direct-SQL bypass.
- Writer lock **до читання**, `measurement/element/line/point` optimistic CAS, idempotent retry same operation UUID + same payload, different-payload retry fail-closed, no replay після uncertain outcome; тільки факт успішного **outer rollback** дозволяє розблокувати редагування. Same-UUID retry звіряє результат, не повторює запис. Deletion/tombstones/parent updates атомарно узгоджують child rows та summary/Flow. SQLDelight reactive invalidation для line updates.
- Фізично зберегти **всі** існуючі v11 дані й міграційні лінії: historical point UUID/anchors/walls/needsReview/unresolved/receipts, measurement geometry, прайс/категорії, кошториси/PDF, SQLCipher keys, WAL, backups, restore, не змінювати portable backup format. Вихід **v9→v10→v11→v12** і обидві відомі deployed v10 fingerprints повинен лишитися робочим; нова migration/fresh schema строго еквівалентні. Не переписувати `9.sqm`/`10.sqm` чи їхні historical fixtures. Unsupported/partial/hybrid version — fail closed, без reset/reseed/key recreation. Додати фізичну v11 fixture (schema + rows), full fingerprint та rollback proof.

## 7. Чіткі межі та наступні етапи

**Не в P3C4:** площинні об'єкти/отвори/вентканали/обводи (#71, наступний P3C5); 2D boolean subtraction, зміна area/perimeter від ліній; фінансовий pricing, нові кошториси, редагування PDF (#44); довільні кути самого outline й геометричний solver (#70); повний UX redesign (#95); runnable iOS host (#42); синхронізація між пристроями. Прямолінійний сегмент, optional width — **не** гарантія перевіреної геометрії ніші/вирізу.

Після реалізації: оновити `AGENTS.md`, початок `docs/PROJECT_ROADMAP.md` і цей task/PR фактичним status, документувати інваріанти, зрозумілий follow-up для P3C5/P4. Якщо технічно треба поділити програмування на кілька комітів — нормально, але весь користувацький сценарій, atomic Save і тести є **єдиною межею приймання**; не видавати неповний етап за готовий.

## Definition of Done

- [ ] Працює LINE за `CatalogSelection` UUID з `м.п.`; реальні segment UUID/мм/anchors, 2+ сегменти, збереження після restart та restore.
- [ ] Один CMP Canvas, normal/fullscreen: selection ↔ item, наближені/точні відстані, edit/delete/undo, коректний pointer/zoom.
- [ ] Автоматичний measured line length; **declared quantity окрема** і змінюється тільки явною дією, 0/partial/mixed/unknown/range не підмінені.
- [ ] Contour+POINT+LINE один атомарний validated Save; wall identity, review/later, sticky unresolved, CAS/idempotency, encrypted schema v12 і безпечна міграція.
- [ ] Усі потрібні common/CMP/Android/Windows/iOS SQLCipher перевірки та final-SHA CI green; owner **окремо** підтвердив Android APK.
- [ ] Не змінені історичні кошториси/PDF, ціноутворення, SQLCipher key/WAL/portable backup; P3C5/P4/#95 залишилися окремими.

**ПРАВИЛО:** чинні P3C3 гарантії безпеки даних/паралельності важливіші за швидкий UI. Жодних direct-main commits, auto-merge, закриття umbrella issues або позначення ручного APK checklist без власника.
