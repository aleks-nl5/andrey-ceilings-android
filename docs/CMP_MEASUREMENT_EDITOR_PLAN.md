## Рішення щодо тестових даних

Власник підтвердив 03.11.2026: уся поточна БД тестова, важливих користувацьких записів немає. **Сумісність із застарілими кресленнями, старими тестовими JSON, Room/Go БД і тестовими архівами НЕ є вимогою наступних PR; жодних міграцій чи додаткових compatibility layers лише заради старих даних.** Можна видаляти / створювати заново *тестові дані*, лише після явного визначення обсягу, не виконувати destructive reset автоматично в застосунку чи CI. У разі суперечності старих історичних чеклістів це рішення має пріоритет для PR A/B.

Це **не скасовує** поточні контракти KMP геометрії, вимірювання у цілих міліметрах, SQLDelight/SQLCipher, UUID/timestamps/soft-delete, чинний формат збереження нових замірів, WAL, backup/restore, чинні незмінні ревізії кошторисів і PDF. Не псувати нові записи й чинні розрахунки заради спрощення старої сумісності.

## Цільова архітектура

- Один `shared/commonMain` CMP Editor + KMP UI-state/presenter/validation. Android, Windows і майбутній runnable iOS host використовують ті самі модель, екран, валідацію та репозиторій.
- Застосовувати наявні `CeilingShapeTemplates`, `VerifiedCeilingGeometry`, `FrozenPolygonGeometryContract`, `OrthogonalSideContour`, `MeasurementGeometryCodec`, `MeasurementDrawing`; жодних дубльованих формул або окремого геометричного рушія для форми.
- Користувач вводить **довжини й повороти**, ніколи не вводить технічні координати X/Y; підтримуються **лише фактично реалізовані** rectangle, l_shaped і polygon (сторони + LEFT/RIGHT 90°, повний замкнений контур). T/U/трапеції, непрямі кути, діагоналі, графічне креслення пальцем — окремі майбутні задачі.
- Поточна точність налаштувань застосовується **лише до нового заміру**; зафіксована точність роботи не змінюється після створення. Відображення інших даних не запускає перерахунок або модифікацію.
- Реальні SQLDelight MeasurementRepository, Flow, транзакції, глобальний UUID, timestamps/tombstones; без фіктивних даних. Windows adapter після #68 підтримує `RETURNING`.
- Reuse `CeilingsScreenScaffold`, `CeilingsFab`, theme/insets/Inter; не порушувати Project Details адресу/FAB/docking/30% snap, незалежну прокрутку Objects/Clients та native Back.

## Затверджена UX-візія точного двостороннього редактора (03.11.2026)

**Обов'язкові вимоги кінцевого продукту, НЕ всі в PR A.** Один спільний KMP геометричний draft є джерелом істини для числових полів, CMP-креслення, селекції, підрахунків і збереження. Креслення — головна область; сторони/властивості згорнуті й відкриваються контекстно; перегляд уже створеного заміру **read-only за замовчуванням**. Редагування вмикається явною дією. **Повний екран — незалежний перемикач подання**, сам по собі не змінює read-only. У fullscreen — тільки креслення, компактна контекстна палітра, «Вписати», zoom/pan, undo/redo, Save/Cancel при редагуванні; Android touch і Windows mouse/keyboard мають рівноправні дії. Вибір сторони/об'єкта на Canvas синхронно вибирає її поле у панелі, а зміни у панелі відображаються на Canvas; ніяких двох різних геометрій.

### Непрямі кути — обов'язковий вимикач 90° snap ([#70](https://github.com/aleks-nl5/andrey-ceilings-android/issues/70))

- Перемикач **«Прямі кути / Довільні кути»** у режимі редагування. У першому режимі — чинні LEFT/RIGHT 90° й ортогональний builder; у другому — **виміряні довжини + явні значення кутів і/або достатні діагоналі/контрольні відрізки**. Одних довжин не вистачає для однозначного довільного багатокутника.
- Точна KMP-модель має перевіряти достатність параметрів, замкненість, самоперетин, допустиму похибку/точність і незмінність введених величин. Заборонено без попередження автоматично «підганяти» останню сторону або кут. Піксельне перетягування — лише інструмент чернетки; остаточні розміри задаються вимірюваннями.
- Контур/формат довільних кутів потребує **окремого versioned domain contract**, не вдавати, що поточний v3 `lengthMm + LEFT/RIGHT` підтримує довільні кути. Не робити фіктивного toggle, який не змінює обчислення. Сумісність зі старими **тестовими** JSON не потрібна.
- **Реалізація:** у PR A не цементувати тип повороту 90° як універсальну UI-архітектуру, але поки створювати лише підтримувані форми. PR B — fullscreen/edit/read-only/selection foundation. **Наступний профільний PR C** — реальні довільні кути, constraint solver, drag/resize і двостороння точна синхронізація до оголошення «повного редактора». Тести нерівнопрямих кутів/недостатніх вимірів/closure обов'язкові.

### Додаткові елементи стелі на кресленні й у калькуляторі ([#71](https://github.com/aleks-nl5/andrey-ceilings-android/issues/71), [#53](https://github.com/aleks-nl5/andrey-ceilings-android/issues/53))

- Користувач може **додавати, вибирати, переміщувати, редагувати точні параметри й видаляти** світильники, люстри, обводи/труби, ніші, вентиляційні канали та подальші типи (світлові лінії, карнизи тощо). У fullscreen доступні hit targets, контекстні розміри, прив'язки до стін/центру, точне числове введення, Undo/Redo; у read-only — тільки перегляд/вибір без зміни даних.
- Один **типізований розширюваний KMP об'єкт**, не намальована іконка: stable UUID/type/code, point/line/area geometry, розміри мм (діаметр/ширина/довжина/глибина за видом), положення, орієнтація, необов'язкові wall anchors/offsets, властивості та примітка. **Measurement outline** та **feature overlay** логічно окремі шари одного креслення.
- Калькулятор має використовувати **ті самі** об'єкти й їхні параметри: коди та одиниці з прайсу (#44), кількість/метраж/площу обчислювати тільки за наявності перевіреного правила відповідного виду. Жодного подвійного нарахування. Розміщення «обводу/отвора» не змінює автоматично площу/периметр без реалізованої точного правила геометричного віднімання. Історичні immutable estimate/PDF snapshots не переписувати.
- **PR A:** передбачити чисту межу outline/overlay у контракті/архітектурі; **без** реалізації всього каталогу. **Окремий PR D / декілька коротких PR** після фундаменту редактора: KMP модель і збереження типізованих елементів → інтерактивне розміщення/редагування на CMP Canvas → зв'язок із калькулятором і прайсом #44. Не заявляти, що feature placement готовий після PR A/B.

### Позначення вершин і сторін літерами — вимога вже для PR A

- **Користувацькі підписи сторін — не номери.** Позначати вершини послідовними **латинськими великими літерами** `A`, `B`, `C`, `D`..., а стіну — **парою сусідніх вершин**: `AB`, `BC`, `CD`, `DA` у замкненому прямокутнику. Для шестикутного контуру: `AB`, `BC`, `CD`, `DE`, `EF`, `FA`. Не пропускати суміжні вершини (не `AB, CD, EF`).
- Одна **спільна чиста KMP функція** формує імена за **упорядкованим контуром** для CMP форми, Canvas, легенди, повідомлень валідації та майбутнього калькулятора. Для понад 26 вершин застосувати `A…Z, AA, AB…`; щоб складені позначення були однозначними, на межі `Z`/`AA` й далі писати `Z–AA`, `AA–AB` (для однолітерних — компактно `AB`). Замикати останню до першої.
- Назви **є похідними підписами**, не persistent ID стіни, не ключами БД і не індексами для прайс-позицій чи прив'язок елементів. Після вставлення/видалення вершини назви перемарковуються узгоджено, але стабільні ID геометричних/додаткових елементів не губляться.
- У PR A при введенні показувати `Сторона AB`, `Сторона BC`, ... замість `Сторона 1`; на CMP кресленні підписувати вершини/сторони узгоджено з тими самими полями. У read-only деталей — така сама легенда. На вузькому Canvas допустимо приховати конфліктні підписи за наявності доступної **повної легенди** з усіма сторонами.
- Тести: 4/6 вершин, замикання, зміна кількості/порядку, 26/27/128 вершин, ті самі підписи у form/drawing/legend, жодних цифрових side-number labels у новому CMP Editor. Не переробляти legacy Android editor у PR A, він залишиться до PR B.
