## Data and interaction

- Schema v25 adds calendar tables, indexes, stable standard types and business settings using migration `24.sqm`. The production schema verifier checks the calendar DDL fingerprint and validates stored calendar schedules when opening, migrating or verifying an encrypted snapshot.
- Local dates, daily schedules and IANA zones drive recurrence. An occurrence keeps its root and original date through an individual move. Forward changes stop old segments and use the shift between scheduled dates and original dates to keep exact routes stable. They remap unambiguous exceptions, preserve terminal history and keep separately edited active exceptions as standalone records when they cannot be remapped.
- Saves check root versions, linked entities and overlaps in a writer transaction. Conflicts use half-open instant intervals. Long-running rules are checked over a rolling 90-day window and one-off work is checked on its exact dates. Date-only work has no blocking interval. If a DST gap pushes a start past its requested end, the interval keeps the requested wall-clock duration and the form displays a clock-change warning.
- Calendar-backed deletion confirmation carries the current set of affected records and versions. The transaction rechecks that set before truncating series, recording historical details, retaining removed ceilings or detaching a client. Existing project, customer and approved-quote guards run in the writer path, including direct repository calls.
- The shared week/month/list screen and explicit-save form use the existing CMP scaffold and resource classes. Android, desktop dashboard and project details use real work references. Android global search preserves its source dialog when opening an exact occurrence. The Android display mode belongs to device preferences. Business settings follow encrypted backup and restore.
- The session cache holds up to eight date ranges and prefetches adjacent periods. The UI clock updates display state without recurring SQL ticks. Restore invalidates the outgoing calendar session before closing its driver.
- A Linux in-memory SQLite 3.53.1 check of the candidate query used 12,000 standalone rows, 200 sparse monthly rules and 1,000 moved exceptions. The 42-day sample returned 262 candidate rows. Over 120 executions the median was 0.252 ms and p95 was 0.405 ms. The query plan used all three range indexes and looked up exceptions by override UUID. This measures candidate selection on Linux SQLite. End-to-end SQLCipher read/expansion and phone rendering require separate measurements.
